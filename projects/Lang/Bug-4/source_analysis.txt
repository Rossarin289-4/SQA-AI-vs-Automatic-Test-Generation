Apache Commons Lang

PROJECT ID:
Lang

BUG:
Lang-4

BUG REPORT:
LANG-882

CLASS:
org.apache.commons.lang3.text.translate.LookupTranslator

METHOD:
translate(CharSequence input, int index, Writer out)

DEFECT MECHANISM:
The buggy implementation stores lookup keys directly as CharSequence objects in a HashMap<CharSequence, CharSequence>.

During translation, the method creates a subsequence from the input:
input.subSequence(index, index + i)

The resulting subsequence is used directly as the HashMap lookup key.

This creates a defect when the stored lookup key and the generated subsequence contain the same characters but are different CharSequence implementations/objects whose equality and hash behavior are not content-equivalent.

The Defects4J trigger demonstrates this with StringBuffer as both lookup key and input. The input subsequence becomes a String, while the stored key remains a StringBuffer. The lookup therefore fails and translate() returns 0 instead of consuming the matched characters.

FIX:
The fixed implementation changes the map key type to String and converts lookup keys using seq[0].toString().

It also converts the input subsequence using subSeq.toString() before performing the lookup.

Therefore equivalent character content is normalized to String before HashMap lookup.

PRIMARY DEFECT BEHAVIOR:
Equivalent character content represented by different CharSequence implementations should still be recognized as the same lookup key.

EXPECTED BUGGY BEHAVIOR:
translate() may return 0 and produce no translated output for equivalent content represented by incompatible CharSequence implementations.

EXPECTED FIXED BEHAVIOR:
translate() recognizes the equivalent character content, writes the mapped value, and returns the number of consumed characters.

TEST DESIGN FOCUS:
1. CharSequence implementation differences.
2. StringBuffer lookup keys with String input.
3. StringBuilder lookup keys with String input.
4. Lookup success with ordinary String keys as a regression baseline.
5. Correct returned character-consumption count.
6. Correct translated output.
7. Multiple lookup entries and greedy matching.
8. Matching from a non-zero input index where appropriate.
9. Regression behavior for normal String-to-String lookup.
