# Closure — การสร้างชุดทดสอบด้วย ChatGPT

## ภาพรวม

ส่วน ChatGPT ของโปรเจกต์นี้ศึกษาการใช้ AI สร้างชุดทดสอบสำหรับบั๊กในโครงการ **Closure จาก Defects4J** โดยดึงข้อมูลบั๊กและโค้ดที่เกี่ยวข้องมาเป็นบริบท แล้วส่งให้ ChatGPT ผ่านหน้าสนทนาเพื่อสร้างโค้ดทดสอบโดยตรง จากนั้นนำชุดทดสอบไปประเมินกับโปรแกรมเวอร์ชันที่มีบั๊ก (buggy) และเวอร์ชันที่แก้ไขแล้ว (fixed) และรวบรวมผลใน `result_chatGPT.csv`

วิธีสร้างเทสของส่วนนี้จึงเป็น **การสร้างเทสด้วย ChatGPT ผ่านการสนทนา (chat-based test generation)** ซึ่งมีผู้ดำเนินการเตรียมข้อมูล ส่งข้อความ และนำโค้ดที่ได้ไปใช้งาน

## เหตุผลที่ใช้ ChatGPT ผ่านหน้าสนทนา

ระหว่างดำเนินงานพบข้อจำกัดด้านลิมิตและโควต้าของ API ทำให้ไม่สามารถใช้ API สร้างชุดทดสอบต่อเนื่องได้ตามแผน จึงปรับขั้นตอนโดยนำข้อมูลบั๊กที่ดึงจาก Defects4J ส่งให้ ChatGPT สร้างเทสผ่านหน้าสนทนาโดยตรง เพื่อให้งานทดลองสามารถดำเนินต่อได้ภายใต้ข้อจำกัดดังกล่าว

การปรับนี้ยังคงใช้ AI เป็นผู้สร้างโค้ดทดสอบ แต่เปลี่ยนช่องทางการส่งข้อมูลและรับโค้ด จึงควรระบุวิธีนี้แยกจากการสร้างเทสด้วย API แบบอัตโนมัติเมื่อรายงานผล

## ขั้นตอนการดำเนินงาน

1. **ดึงข้อมูลบั๊กจาก Defects4J** ระบุรหัสบั๊กของ Closure และรวบรวมข้อมูลบั๊กกับโค้ดที่เกี่ยวข้อง เพื่อใช้เป็นบริบทในการสร้างชุดทดสอบ
2. **ส่งข้อมูลให้ ChatGPT** นำบริบทดังกล่าวใส่ในข้อความสนทนา และขอให้สร้างโค้ดทดสอบสำหรับพฤติกรรมที่เกี่ยวข้องกับบั๊ก
3. **นำโค้ดทดสอบไปใช้งาน** จัดเก็บโค้ดที่ได้รับเป็นไฟล์ทดสอบ ตรวจสอบให้เข้ากับโครงสร้างโปรเจกต์ และเตรียมสำหรับการคอมไพล์และรัน
4. **ประเมินบน buggy และ fixed** ใช้เทสชุดเดียวกันกับทั้งสองเวอร์ชัน เพื่อพิจารณาว่าเทสสามารถแสดงความแตกต่างของพฤติกรรมก่อนและหลังการแก้บั๊กได้หรือไม่
5. **รวบรวมผลการทดสอบ** สรุปจำนวนเทส การตรวจพบบั๊ก ค่า coverage และเวลาที่มีข้อมูลในผลต้นฉบับ แล้วรวมผลรอบ 1 เป็นไฟล์ `result_chatGPT.csv`

การได้รับโค้ดจาก ChatGPT เป็นขั้นตอนการสร้างชุดทดสอบ ส่วนข้อสรุปว่าเทสตรวจพบบั๊กได้ต้องอาศัยผลการรันจริง เทสที่รันไม่ผ่านเพราะคอมไพล์ไม่ได้หรือสภาพแวดล้อมมีปัญหาไม่เพียงพอสำหรับยืนยันการตรวจพบบั๊ก

## เกณฑ์การตรวจพบบั๊ก

เทสที่ใช้ยืนยันการตรวจพบบั๊กควร **ผ่านใน fixed version และล้มเหลวใน buggy version จากพฤติกรรมของบั๊ก** โดยใช้เทสเดียวกัน หากเทสผ่านทั้งสองเวอร์ชัน จะยังไม่สามารถยืนยันว่าเทสนั้นตรวจพบบั๊กเป้าหมายได้

ค่า coverage แสดงส่วนของโค้ดที่เทสได้เรียกใช้งาน จึงควรพิจารณาควบคู่กับผลการตรวจพบบั๊ก เพราะ coverage สูงเพียงอย่างเดียวไม่ได้ยืนยันว่า assertions ของเทสตรวจพบพฤติกรรมที่ผิดได้

## ไฟล์ผลลัพธ์

`result_chatGPT.csv` รวมแถวสรุปจากไฟล์ `result.csv` ของแต่ละบั๊กใน `Result_Round1.zip` เป็น CSV เดียว โดยคงค่าจากต้นฉบับและเรียงตามเลขบั๊ก มี 170 แถว ครอบคลุม Closure-1 ถึง Closure-170

| คอลัมน์ | ความหมายในไฟล์สรุป |
| --- | --- |
| `bug_id` | รหัสบั๊ก เช่น Closure-1 |
| `source` | แหล่งที่มาของชุดทดสอบ ระบุเป็น ChatGPT |
| `round` | รอบของผลทดลอง ชุดนี้เป็นรอบ 1 |
| `source_run` | ตัวระบุที่มาของข้อมูลผลรันจากต้นฉบับ |
| `test_count` | จำนวนรายการทดสอบที่ต้นฉบับสรุปไว้ |
| `detected_tests` | จำนวนรายการทดสอบที่ต้นฉบับระบุว่าตรวจพบบั๊ก |
| `detected` | สถานะการตรวจพบบั๊ก: YES, NO หรือ N/A |
| `buggy_fail_tests` | จำนวนรายการทดสอบที่ล้มเหลวบน buggy ตามต้นฉบับ |
| `fixed_pass_tests` | จำนวนรายการทดสอบที่ผ่านบน fixed ตามต้นฉบับ |
| `coverage_matched_tests` | จำนวนรายการทดสอบที่จับคู่กับข้อมูล coverage ได้ตามต้นฉบับ |
| `mean_line_pct` | ค่าเฉลี่ย line coverage (%) ที่ต้นฉบับรายงาน |
| `mean_condition_pct` | ค่าเฉลี่ย condition coverage (%) ที่ต้นฉบับรายงาน |
| `execution_ms` | ค่าเวลาประมวลผลที่ต้นฉบับรายงาน หน่วยมิลลิวินาที |
| `status` | สถานะข้อมูลผลลัพธ์จากต้นฉบับ |

ค่า coverage ในไฟล์เป็นค่าเฉลี่ยที่ต้นฉบับรายงาน ไม่ควรตีความเป็น coverage รวมของ Closure ทั้งโครงการ ส่วน `execution_ms` ไม่มีข้อมูลเพียงพอใน CSV สำหรับยืนยันว่ารวมเวลาเตรียมข้อมูล สนทนา และสร้างเทสด้วย ChatGPT แล้ว

### สถานะของผลรอบ 1

| รายการ | จำนวนบั๊ก |
| --- | ---: |
| แถวสรุปทั้งหมด | 170 |
| มีสถานะ VERIFIED_RESULTS ตามต้นฉบับ | 168 |
| ตรวจพบบั๊ก (`detected = YES`) | 166 |
| ไม่ตรวจพบบั๊ก (`detected = NO`) | 2 |
| ไม่มีข้อมูลผล (`NO_RESULT_DATA`) | 2 |

บั๊กที่ระบุว่าไม่ตรวจพบคือ **Closure-47 และ Closure-113** ส่วน **Closure-63 และ Closure-93** ไม่มีข้อมูลผลในชุดนี้ การไม่มีข้อมูลผลต้องแยกจากกรณีที่มีผลรันแล้วไม่ตรวจพบบั๊ก และค่า `N/A` ไม่ควรแทนด้วยศูนย์

สถานะ `VERIFIED_RESULTS` เป็นค่าที่ได้รับจากไฟล์ต้นฉบับ การรวม CSV และการเขียน README นี้ไม่ได้รันทดสอบบั๊กทั้งหมดใหม่

## ข้อจำกัดและการเปรียบเทียบผล

- **มีขั้นตอนที่ผู้ดำเนินการทำผ่านหน้าสนทนา:** วิธีนี้มีการเตรียมและส่งข้อมูลให้ ChatGPT โดยตรง จึงมีความแตกต่างจากกระบวนการเรียก API อัตโนมัติ
- **การทำซ้ำต้องอาศัยหลักฐานการสร้างเทส:** ควรเก็บข้อความที่ส่งให้ ChatGPT โค้ดที่ได้รับ การแก้ไขโค้ด และข้อมูลโมเดลที่ยืนยันได้ เพื่ออธิบายที่มาของแต่ละชุดทดสอบ
- **เวลาในการสร้างเทสยังสรุปจาก CSV นี้ไม่ได้:** ไม่ควรใช้ `execution_ms` เป็นเวลา end-to-end ของ ChatGPT หรือเปรียบเทียบโดยตรงกับ search budget ของ SA/BPSO
- **ต้องพิจารณาบริบทที่ AI ได้รับ:** หากข้อความที่ส่งให้ ChatGPT มีแพตช์หรือโค้ด fixed version ควรเปิดเผยไว้ เพราะเป็นข้อมูลเกี่ยวกับการแก้บั๊กที่อาจต่างจากบริบทของวิธีอื่น
- **ไฟล์ระบุแหล่งที่มาเป็น ChatGPT:** CSV ชุดนี้ไม่ได้ระบุรหัสโมเดลเฉพาะ จึงไม่สามารถยืนยันรุ่นของโมเดลจากไฟล์นี้เพียงอย่างเดียว

เมื่อนำไปเปรียบเทียบกับ SA, BPSO หรือ AI ผ่าน API ควรระบุความแตกต่างของขั้นตอนสร้างเทส ข้อมูลนำเข้า และขอบเขตการวัดเวลา พร้อมใช้เกณฑ์ประเมิน buggy/fixed และ coverage ที่สอดคล้องกัน

## ข้อความอธิบายสำหรับรายงาน

> สำหรับโครงการ Closure ผู้จัดทำใช้ ChatGPT สร้างชุดทดสอบผ่านหน้าสนทนาโดยตรง เนื่องจากกระบวนการสร้างเทสผ่าน API ประสบข้อจำกัดด้านลิมิตและโควต้า โดยดึงข้อมูลบั๊กและโค้ดที่เกี่ยวข้องจาก Defects4J มาเป็นบริบทให้ ChatGPT สร้างโค้ดทดสอบ จากนั้นนำชุดทดสอบไปประเมินกับโปรแกรมเวอร์ชันที่มีบั๊กและเวอร์ชันที่แก้ไขแล้ว และรวบรวมผลการตรวจพบบั๊กและค่า coverage ที่มีข้อมูลไว้ในไฟล์ผลลัพธ์ วิธีนี้เป็นการสร้างเทสด้วย AI ผ่านการสนทนาที่มีผู้ดำเนินการเตรียมข้อมูลและนำโค้ดไปใช้งาน จึงรายงานแยกจากการสร้างเทสด้วย API แบบอัตโนมัติ
