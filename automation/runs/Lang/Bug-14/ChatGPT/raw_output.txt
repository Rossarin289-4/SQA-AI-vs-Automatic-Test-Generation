## 1. Behavior that differs

The defect is in `StringUtils.equals(CharSequence, CharSequence)`.

The issue reported as LANG-786 is that after the method was changed from accepting `String` to accepting general `CharSequence`, the implementation still relied on `CharSequence.equals(Object)`. The Java `CharSequence` contract does **not** require different `CharSequence` implementations to consider each other equal, even when they contain exactly the same characters. ([Apache Issues][1])

For example:

```text
StringBuilder("hello")
String("hello")
```

represent the same character sequence, but `StringBuilder.equals(String)` is not a character-by-character comparison.

Therefore, the intended behavior of `StringUtils.equals` is:

> Two non-null `CharSequence` objects are equal when they have the same length and the same characters in the same positions.

The modern Apache implementation follows this character-by-character approach for non-`String` `CharSequence` objects. ([GitHub][2])

## 2. Likely root cause visible from the source

The root cause is the use of the generic `equals()` operation on a `CharSequence` instead of comparing its characters.

Conceptually, the buggy implementation behaves like:

```java
if (cs1 == null) {
    return cs2 == null;
}
return cs1.equals(cs2);
```

This works when both objects are `String`, because `String.equals()` compares character contents.

It does **not** work reliably for arbitrary `CharSequence` implementations such as `StringBuilder` or `StringBuffer`.

The corrected implementation needs to compare:

1. object identity,
2. `null`,
3. length,
4. each character with `charAt(i)`.

That is consistent with the documented issue and the later implementation of `StringUtils.equals`. ([Apache Issues][1])

## 3. Specific behavior the generated tests should distinguish

The key distinction is:

```text
StringUtils.equals(CharSequence A, CharSequence B)
```

where **A and B are different `CharSequence` implementations but contain the same characters**.

The most direct independent example is:

```text
StringBuilder("alpha")
String("alpha")
```

Expected:

```text
true
```

### Why this detects the defect

**BUGGY**

```java
StringBuilder("alpha").equals("alpha")
```

returns `false`, so:

```java
StringUtils.equals(new StringBuilder("alpha"), "alpha")
```

returns `false`.

**FIXED**

The implementation compares the five characters:

```text
a == a
l == l
p == p
h == h
a == a
```

so it returns `true`.

This gives the required:

```text
BUGGY  → FAIL
FIXED  → PASS
```

A second independent form is useful:

```text
StringUtils.equals(new StringBuilder("delta"),
                   new StringBuilder("delta"))
```

The two `StringBuilder` objects have identical character contents but are different objects. The buggy implementation relies on `StringBuilder.equals`, which does not provide content equality between the two objects. The fixed implementation compares their characters.

## 5. JUnit 4.12 test code

The class uses only the public `StringUtils.equals(CharSequence, CharSequence)` API. It does not use reflection, the original trigger test, or any production-code modification.

```java
package org.apache.commons.lang3;

import static org.junit.Assert.assertFalse;
import static org.junit.Assert.assertTrue;

import org.junit.Test;

public class StringUtilsLang14Test {

    @Test
    public void testEqualsStringBuilderWithString() {
        CharSequence first = new StringBuilder("alpha");
        CharSequence second = "alpha";

        assertTrue(StringUtils.equals(first, second));
    }

    @Test
    public void testEqualsStringWithStringBuilder() {
        CharSequence first = "bravo";
        CharSequence second = new StringBuilder("bravo");

        assertTrue(StringUtils.equals(first, second));
    }

    @Test
    public void testEqualsDifferentStringBuildersWithSameContent() {
        CharSequence first = new StringBuilder("delta");
        CharSequence second = new StringBuilder("delta");

        assertTrue(StringUtils.equals(first, second));
    }

    @Test
    public void testEqualsEmptyStringBuilderWithEmptyString() {
        CharSequence first = new StringBuilder();
        CharSequence second = "";

        assertTrue(StringUtils.equals(first, second));
    }

    @Test
    public void testEqualsDifferentCharSequenceContent() {
        CharSequence first = new StringBuilder("echo");
        CharSequence second = "ecHo";

        assertFalse(StringUtils.equals(first, second));
    }

    @Test
    public void testEqualsNullAndNonNullCharSequence() {
        CharSequence first = null;
        CharSequence second = new StringBuilder("foxtrot");

        assertFalse(StringUtils.equals(first, second));
    }
}
```

### Root cause

The buggy implementation treats `CharSequence.equals()` as if all `CharSequence` implementations had a common content-based equality contract. They do not. LANG-786 specifically identifies this as undefined behavior for different `CharSequence` implementations. ([Apache Issues][1])

### Targeted behavior

The generated tests require:

```text
same characters + same length
        ↓
StringUtils.equals(...) == true
```

even when the two inputs are different `CharSequence` implementations.

### Number of tests

**6 tests total**

* **4 defect-detecting tests**
* **2 regression tests**

The four detecting tests intentionally vary the direction and representation of the `CharSequence` operands rather than repeating one identical input pattern.

### Independence from the original trigger

The suite does **not** use:

* the original `StringUtilsEqualsIndexOfTest::testEquals`,

* `javax.lang.model.element.Name`,
* reflection,

* modified production code.

Instead, it derives the test condition directly from the source-level defect: **different `CharSequence` implementations containing identical characters must compare equal**.
