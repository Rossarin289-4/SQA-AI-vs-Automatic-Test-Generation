## 1. Behavior that differs

The defect is in how `NumericEntityUnescaper.translate()` finds the **end of a numeric entity** when the entity does **not have a terminating semicolon**.

The buggy implementation does:

```java
while(input.charAt(end) != ';') {
    end++;
}
```

It assumes that a `';'` will eventually occur. If the numeric entity reaches the end of the input without a semicolon, `end` eventually becomes `input.length()`, and the next `charAt(end)` throws `StringIndexOutOfBoundsException`.

The fixed implementation instead bounds the scan:

```java
while(end < seqEnd && (...numeric character checks...)) {
    end++;
}
```

and subsequently determines whether a semicolon is actually present:

```java
boolean semiNext = (end != seqEnd) && (input.charAt(end) == ';');
```

This means the corrected implementation supports numeric entities that terminate simply because the input ends, as well as entities followed by non-numeric text. The LANG-710 JIRA report documents the original failure as a `StringIndexOutOfBoundsException` for an unfinished numeric entity at the end of the input. ([Apache Issues][1])

---

## 2. Likely root cause visible from the source

There are two related problems in the buggy implementation.

### A. Unbounded search for `;`

The central problem is:

```java
int end = start;

while(input.charAt(end) != ';') {
    end++;
}
```

There is no `end < seqEnd` condition.

Therefore, for an entity such as:

```text
&#90
```

the loop reaches the end of the string and attempts:

```java
input.charAt(input.length())
```

which is outside the valid index range.

The fixed implementation explicitly prevents this by checking `end < seqEnd`.

### B. The buggy code assumes every entity has `;`

The class documentation says that the semicolon is optional:

```text
&#[xX]?\d+;?
```

So an entity ending at the end of the input should be a valid candidate for translation.

The fixed implementation correctly treats the semicolon as optional by scanning the numeric portion and then checking whether a semicolon happens to follow it.

This is the important behavioral contract that the generated tests should target.

## 3. Specific behavior that a generated test should distinguish

The tests should distinguish these cases:

1. **Decimal numeric entity ending exactly at end-of-input without `;`**

   * Example structure: `&#<digits>`
   * Should be translated.

2. **Hexadecimal numeric entity ending exactly at end-of-input without `;`**

   * Example structure: `&#x<hex-digits>`
   * Should be translated.

3. **Numeric entity without `;` followed by ordinary text**

   * The numeric portion should be translated and the following text should remain.
   * This is particularly useful because the fixed code stops scanning when the next character is no longer a valid numeric digit.

4. **Hexadecimal entity without `;` followed by ordinary text**

   * Same boundary behavior for the hexadecimal branch.

5. **Incomplete hexadecimal prefix**

   * Example structure: `&#x` at the end.
   * The fixed implementation explicitly checks `start == seqEnd` and returns `0`, rather than throwing an exception.

These cases are derived from the changed source logic rather than from the named trigger tests.

---

## 4. Boundary, representative, and regression cases

I recommend **five tests**.

| Test | Case                            | Expected behavior                   |
| ---- | ------------------------------- | ----------------------------------- |
| 1    | Decimal entity at end, no `;`   | Decode the decimal value            |
| 2    | Hex entity at end, no `;`       | Decode the hexadecimal value        |
| 3    | Decimal entity followed by text | Decode only numeric prefix          |
| 4    | Hex entity followed by text     | Decode only hexadecimal prefix      |
| 5    | `&#x` at end                    | Leave input unchanged; no exception |

For example, independently chosen values can be:

* `&#90` → `Z`
* `&#x4A` → `J`
* `&#90tail` → `Ztail`
* `&#x4Atail` → `Jtail`

These deliberately do **not** use the original trigger test inputs or expected values.

One subtle point is that the buggy implementation can fail in two different ways:

* For a numeric entity reaching the end of the string, it can throw `StringIndexOutOfBoundsException`.
* For a numeric entity followed by ordinary text but no semicolon, it can consume the text while searching for `;`, causing `NumberFormatException` internally and returning `0`.

The fixed implementation handles both cases because it stops at either the end of the input or the first non-numeric character.

## 6. Defect detection strategy

### Test 1 — decimal entity at end without semicolon

**Input:**

```text
&#90
```

**BUGGY VERSION:**
The `while` loop keeps looking for `;` after the final digit and eventually calls `charAt(input.length())`. Therefore the test is expected to fail with `StringIndexOutOfBoundsException`.

**FIXED VERSION:**
The scan stops when `end == seqEnd`, parses `90`, and returns `"Z"`.

**Detection:** BUGGY fails, FIXED passes.

---

### Test 2 — hexadecimal entity at end without semicolon

**Input:**

```text
&#x4A
```

**BUGGY VERSION:**
Again, there is no semicolon. The unbounded loop runs past the end of the input and throws `StringIndexOutOfBoundsException`.

**FIXED VERSION:**
The hexadecimal digits are scanned up to the end of the input, parsed as hexadecimal, and translated to `"J"`.

**Detection:** BUGGY fails, FIXED passes.

This complements Test 1 by checking the separate hexadecimal branch.

---

### Test 3 — decimal entity followed by text

**Input:**

```text
&#90tail
```

**BUGGY VERSION:**
The buggy loop does not stop at the first non-numeric character. It continues searching for `;`, so it attempts to parse something equivalent to the entire substring after `&#`. That is not a valid decimal number. The method catches `NumberFormatException` and returns `0`.

Consequently, the surrounding `CharSequenceTranslator` machinery leaves the input unchanged rather than producing the desired `"Ztail"`.

**FIXED VERSION:**
The scan stops after `90` because `t` is not a decimal digit. It translates `90` to `Z`, and the remaining `"tail"` remains unchanged.

**Detection:** BUGGY fails, FIXED passes.

---

### Test 4 — hexadecimal entity followed by text

**Input:**

```text
&#x4Atail
```

**BUGGY VERSION:**
The buggy loop continues looking for `;` rather than stopping at the first non-hexadecimal character. The resulting substring cannot be parsed as a hexadecimal integer, so the translator returns `0`.

**FIXED VERSION:**
It recognizes `4A` as the hexadecimal numeric portion, stops at `t`, and produces:

```text
Jtail
```

**Detection:** BUGGY fails, FIXED passes.

This complements Test 3 by exercising the hexadecimal digit scanning logic.

---

### Test 5 — incomplete hexadecimal prefix

**Input:**

```text
&#x
```

**BUGGY VERSION:**
After recognizing `x`, the buggy implementation increments `start` to the end of the string and then enters the unbounded `while` loop. It subsequently accesses beyond the input and throws `StringIndexOutOfBoundsException`.

**FIXED VERSION:**
The new:

```java
if(start == seqEnd) {
    return 0;
}
```

guard recognizes that there are no hexadecimal digits. The translator therefore leaves the input unchanged:

```text
&#x
```

**Detection:** BUGGY fails, FIXED passes.

### Summary

* **Root cause:** `NumericEntityUnescaper` searches for `';'` with an unbounded `charAt(end)` loop.
* **Correct behavior:** numeric entities may terminate at the end of the input or immediately before a non-numeric character because the semicolon is optional.
* **Generated tests:** **5**.
* **Coverage:**

  * decimal/no semicolon
  * hexadecimal/no semicolon
  * decimal followed by text
  * hexadecimal followed by text
  * incomplete hexadecimal prefix
* **Independence:** none of the test cases uses the original trigger test implementation or its exact inputs/expected values.
* The tests exercise `NumericEntityUnescaper.translate(CharSequence)` directly, so the modified production behavior is tested without invoking the original developer tests.

The JIRA record for LANG-710 specifically describes the historical failure as `StringIndexOutOfBoundsException` from `NumericEntityUnescaper.translate()` when processing an entity without a terminating semicolon. ([Apache Issues][1])

### Limitations

The supplied source is enough to identify the principal defect and construct direct tests. The original trigger-test implementation was intentionally not inspected or reproduced, so the exact ground-truth input/output pairs are not used.

One limitation is that the supplied source does not show the surrounding Defects4J test configuration. The proposed tests therefore target the public inherited `translate(CharSequence)` API and rely only on behavior directly visible in the two supplied implementations.

Also, the source's documentation says the semicolon is optional, which strongly supports the no-semicolon cases. The tests with a non-numeric suffix additionally exercise the fixed implementation's newly bounded digit scan rather than merely the end-of-input boundary.
