## 1. The behavior that differs

The defect is in `StringUtils.replaceEach(String, String[], String[])` when **one element of `replacementList` is `null`**.

The intended behavior is that a replacement whose replacement value is `null` is **ignored**, rather than causing a `NullPointerException`. The LANG-552 report explicitly records that `null` inside the replacement array should be ignored. ([Apache Issues][1])

The important detail is that the failure does **not necessarily happen during the first search**. The algorithm searches for the earliest replacement, performs it, and then searches again for remaining replacements. A `null` replacement can therefore survive the first scan and become problematic during a later scan.

---

## 2. The likely root cause visible from the source

The source-level defect is a missing `replacementList[i] == null` guard in the replacement-search logic.

The surrounding implementation is designed to skip entries when:

* the entry has already been exhausted,
* the search string is `null`/empty, or
* the replacement string is `null`.

The corrected implementation needs to consistently skip the third case during the subsequent search as well.

Conceptually, the buggy logic can reach a situation equivalent to:

```text
searchList[i]       = "marker"
replacementList[i]  = null
```

and then later select that index for replacement. Eventually the implementation attempts to append:

```text
replacementList[replaceIndex]
```

which is `null`, producing the defect.

The historical LANG-552 issue confirms that the fix was specifically made so `replaceEach` no longer throws an NPE when `null` appears in the replacement array. ([Apache Issues][1])

## 3. The specific behavior a generated test should distinguish

The generated tests should establish this contract:

> If a search string has a `null` replacement, that particular replacement is ignored, while other valid replacements are still performed.

The strongest distinguishing condition is:

```text
There is at least one valid replacement that happens first,
followed by a searchable entry whose replacement is null.
```

This is important because a `null` replacement by itself may not expose the defect. If there are no valid replacements, the method can finish during its initial search without entering the problematic later-search path.

So the tests below deliberately exercise:

* a null replacement after one valid replacement,
* a null replacement before a valid replacement but encountered after the valid replacement,
* null replacements between multiple valid replacements,
* repeated occurrences of a search string with a null replacement,
* a regression case where all replacement entries are null.

## 6. Defect detection strategy

### `testNullReplacementAfterValidReplacement`

**Input**

```text
text = "red BLUE"
search = ["red", "BLUE"]
replacement = ["green", null]
```

The valid `"red"` replacement is performed first. The implementation then searches for further replacements and encounters `"BLUE"` with a `null` replacement.

* **BUGGY:** throws `NullPointerException`
* **FIXED:** skips the null replacement and returns `"green BLUE"`

**Defect-detecting:** Yes.

---

### `testNullReplacementBeforeLaterValidMatch`

Here the null replacement is the first array entry, but its actual occurrence is after `"START"`.

* **BUGGY:** after replacing `"START"`, the later scan can reach the `"xx"` entry and fail with `NullPointerException`.
* **FIXED:** ignores `"xx"` and returns `"BEGIN xx"`.

**Defect-detecting:** Yes.

---

### `testNullReplacementBetweenTwoValidReplacements`

There are valid replacements on both sides of the null entry.

Expected:

```text
"one TWO three"
→
"1 TWO 3"
```

The `"TWO"` replacement must be ignored.

* **BUGGY:** can throw `NullPointerException` during the later search.
* **FIXED:** performs the two valid replacements and skips `"TWO"`.

**Defect-detecting:** Yes.

---

### `testNullReplacementWithMatchBeforeAndAfterValidReplacement`

The search string `"BAD"` has a null replacement and occurs twice, while `"good"` has a valid replacement between them.

Expected:

```text
"BAD good BAD"
→
"BAD better BAD"
```

This specifically checks that a null replacement remains ignored even when its search string appears both before and after another successful replacement.

* **BUGGY:** can fail when the second `"BAD"` is encountered during the subsequent search.
* **FIXED:** skips `"BAD"` and replaces only `"good"`.

**Defect-detecting:** Yes.

---

### `testOnlyNullReplacementsAreIgnored`

This is a regression/boundary test.

There is nothing that should actually be replaced because every replacement value is `null`.

* **BUGGY:** expected to return the original text in this path.
* **FIXED:** returns the original text.
* **Expected result:** `"keep these words"`

**Defect-detecting:** No, but it verifies that the corrected null-handling behavior does not accidentally modify text.

# Summary

**Root cause:** `replaceEach` does not consistently skip entries whose corresponding replacement value is `null` during its later search phase.

**Targeted behavior:** `null` entries in `replacementList` must be ignored while valid replacement entries continue to work. This matches the documented intent recorded in LANG-552. ([Apache Issues][1])

**Number of generated tests:** **5**

* 4 defect-focused tests
* 1 regression/boundary test

The tests are independent of the trigger because they use different text, search strings, replacement strings, and combinations. They are derived from the observed control-flow defect rather than reproducing the trigger test.
