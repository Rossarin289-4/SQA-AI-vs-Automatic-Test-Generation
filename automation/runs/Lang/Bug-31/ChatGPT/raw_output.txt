## 1. Behavior that differs

The defect is in `StringUtils.containsAny(CharSequence, char[])`.

The **buggy version** treats each UTF-16 `char` independently. Therefore, when the input contains a supplementary Unicode character represented by a **high-surrogate + low-surrogate pair**, matching only the high surrogate is enough to return `true`.

The **fixed version** checks the complete surrogate pair when the matched character is a high surrogate. It only returns `true` when the following low surrogate also matches. ([GitHub][1])

The same correction applies to the `containsAny(CharSequence, String)` path because that overload ultimately searches the characters of the supplied search string.

---

## 2. Likely root cause visible from the source

The buggy implementation essentially does:

```text
for every input char
    for every search char
        if searchChar == inputChar
            return true
```

This is incorrect for supplementary Unicode characters because Java `String` stores them as **two UTF-16 code units**.

For example, conceptually:

```text
Input supplementary character:
[HIGH_A][LOW_A]

Search character:
[HIGH_A][LOW_B]
```

The buggy implementation sees:

```text
HIGH_A == HIGH_A
```

and immediately returns `true`, even though the complete Unicode characters are different.

The fixed implementation adds a pair check: when the current character is a high surrogate, the next character in the input and search sequence must also match. The historical fix shows this explicitly. ([GitHub][1])

---

## 3. Specific behavior the generated test should distinguish

The key oracle should be:

> **Two different supplementary Unicode characters must not be considered a match merely because they share the same high surrogate.**

For example, construct two different supplementary code points using `Character.toChars(...)`:

```text
actual character    = supplementary code point A
different character = supplementary code point B
```

They can have:

```text
same high surrogate
different low surrogate
```

Then:

```text
containsAny(actualCharacter, differentCharacter)
```

must return:

```text
false
```

The buggy implementation returns `true`, while the fixed implementation returns `false`.

This directly exercises the source-level defect without copying the trigger's exact Unicode values or test implementation. The historical commit confirms that the defect concerned incorrect matching of Unicode supplementary characters. ([GitHub][1])

---

## 4. Boundary, representative, and regression cases

I would use **5 tests** with three distinct purposes:

| Test | Case                                                |  BUGGY |   FIXED |
| ---- | --------------------------------------------------- | -----: | ------: |
| 1    | Different supplementary characters through `char[]` | `true` | `false` |
| 2    | Different supplementary characters through `String` | `true` | `false` |
| 3    | Mismatch occurs after ordinary characters           | `true` | `false` |
| 4    | Exact supplementary character through `char[]`      | `true` |  `true` |
| 5    | Exact supplementary character through `String`      | `true` |  `true` |

The first three are **defect-detecting**. The last two are positive regression tests.

The tests intentionally use different code points from the historical trigger. The commit's own added tests used two specific supplementary characters, whereas these tests construct different supplementary characters programmatically. ([GitHub][1])

## 5. Complete JUnit 4.12 test class

```java
package org.apache.commons.lang3;

import static org.junit.Assert.assertFalse;
import static org.junit.Assert.assertTrue;

import org.junit.Test;

public class StringUtilsLang31Test {

    @Test
    public void testContainsAnyCharArrayDoesNotMatchDifferentSupplementaryCharacter() {
        String actualCharacter = new String(Character.toChars(0x1F600));
        String differentCharacter = new String(Character.toChars(0x1F601));

        char[] searchChars = differentCharacter.toCharArray();

        assertFalse(
                StringUtils.containsAny(actualCharacter, searchChars));
    }

    @Test
    public void testContainsAnyStringDoesNotMatchDifferentSupplementaryCharacter() {
        String actualCharacter = new String(Character.toChars(0x1F680));
        String differentCharacter = new String(Character.toChars(0x1F681));

        assertFalse(
                StringUtils.containsAny(actualCharacter, differentCharacter));
    }

    @Test
    public void testContainsAnyCharArrayDoesNotMatchPartialSurrogatePairAfterPrefix() {
        String actualCharacter = new String(Character.toChars(0x1F682));
        String differentCharacter = new String(Character.toChars(0x1F683));

        String input = "prefix" + actualCharacter + "suffix";
        char[] searchChars = {
            'x',
            differentCharacter.charAt(0),
            differentCharacter.charAt(1),
            'y'
        };

        assertFalse(
                StringUtils.containsAny(input, searchChars));
    }

    @Test
    public void testContainsAnyCharArrayMatchesCompleteSupplementaryCharacter() {
        String target = new String(Character.toChars(0x1F642));

        assertTrue(
                StringUtils.containsAny(
                        "before" + target + "after",
                        target.toCharArray()));
    }

    @Test
    public void testContainsAnyStringMatchesCompleteSupplementaryCharacter() {
        String target = new String(Character.toChars(0x1F680));

        assertTrue(
                StringUtils.containsAny(
                        "left" + target + "right",
                        target));
    }
}
```

## 6. Defect detection strategy + summary

### Test 1

`testContainsAnyCharArrayDoesNotMatchDifferentSupplementaryCharacter`

Input contains one supplementary character, while `searchChars` contains a **different** supplementary character with the same high-surrogate structure but a different low surrogate.

* **BUGGY:** `true` ❌
* **FIXED:** `false` ✅

**Defect-detecting.**

---

### Test 2

`testContainsAnyStringDoesNotMatchDifferentSupplementaryCharacter`

Same semantic condition as Test 1, but exercises the `String` search overload rather than directly passing a `char[]`.

* **BUGGY:** `true` ❌
* **FIXED:** `false` ✅

**Defect-detecting.**

This gives coverage of both public input forms involved in the reported issue. The historical fix changed the `char[]` implementation, while the `String` overload uses that character-level behavior. ([GitHub][1])

---

### Test 3

`testContainsAnyCharArrayDoesNotMatchPartialSurrogatePairAfterPrefix`

Places the problematic supplementary character later in a larger string and puts unrelated characters into the search array.

This checks that the implementation does not accidentally report a match merely because a surrogate occurs somewhere inside the string.

* **BUGGY:** `true` ❌
* **FIXED:** `false` ✅

**Defect-detecting.**

---

### Test 4

`testContainsAnyCharArrayMatchesCompleteSupplementaryCharacter`

The complete high-surrogate + low-surrogate pair is present in both the input and search array.

* **BUGGY:** `true` ✅
* **FIXED:** `true` ✅

**Positive regression test.**

It ensures the fix does not simply reject supplementary characters.

---

### Test 5

`testContainsAnyStringMatchesCompleteSupplementaryCharacter`

Same positive condition through the `String` overload.

* **BUGGY:** `true` ✅
* **FIXED:** `true` ✅

**Positive regression test.**

---

### Summary

* **Root cause:** the buggy implementation compares UTF-16 code units independently, so a shared high surrogate can produce a false positive.
* **Targeted behavior:** different supplementary Unicode characters must not match unless their complete surrogate pairs match.
* **Generated tests:** **5**

  * **3 defect-detecting**
  * **2 positive regression tests**
* **Independence:** the tests derive their inputs from the source-level failure mechanism rather than reproducing the supplied trigger tests. They use different Unicode code points and construct the surrogate pairs programmatically.
* **API coverage:** both `char[]` and `String` search forms are exercised.
* **JUnit:** uses only JUnit 4.12-compatible `@Test`, `assertTrue`, and `assertFalse`.
* **No reflection**, production-code modification, or trigger-test invocation is used.

The historical LANG-607 fix confirms that the intended correction was specifically to check the second code unit when a matching character is a high surrogate. ([GitHub][1])

## Limitations

The supplied source excerpt was truncated around the actual `containsAny` implementation, so the exact BUGGY/FIXED method bodies were not fully visible in the prompt. I therefore verified the historical fixed revision directly: commit `1ced894` identifies LANG-607 and shows the exact `containsAny(CharSequence, char[])` change from single-`char` matching to supplementary-character pair matching. ([GitHub][1])

One practical limitation is that the `String` overload's behavior depends on how that overload delegates to the character-array implementation in this Defects4J version. The historical source indicates that the character-array method is the core corrected implementation, so the `char[]` tests are the strongest direct defect oracles.
