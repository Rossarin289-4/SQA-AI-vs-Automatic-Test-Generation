## 1. SOURCE CODE ANALYSIS

### 1.1 Behavior that differs

The important difference is **not actually in the `toString()` method body** in the source shown in the prompt.

The supplied BUGGY and FIXED sources differ in the fields:

**BUGGY**

```java
private Rule[] mRules;
private int mMaxLengthEstimate;
```

**FIXED**

```java
private transient Rule[] mRules;
private transient int mMaxLengthEstimate;
```

The FIXED version also has:

```java
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    init();
}
```

This is consistent with Apache Commons Lang's documented LANG-303 fix: **`FastDateFormat.mRules` was not transient or serializable**. ([Apache Commons][1])

### 1.2 Likely root cause

`FastDateFormat` is serializable through its superclass, but `mRules` contains internal `Rule` objects that are not intended to be serialized.

In the BUGGY version, Java serialization therefore attempts to serialize the internal rule array and can fail with a `NotSerializableException`.

The FIXED version solves this by:

1. Marking `mRules` and `mMaxLengthEstimate` as `transient`.
2. Excluding them from the serialized stream.
3. Rebuilding them using `init()` after deserialization.

So the intended behavior is:

> A configured `FastDateFormat` should be serializable and should still work after being deserialized.

The historical Apache test for LANG-303 also verifies serialization followed by using the deserialized formatter, which is consistent with this source-level diagnosis. ([GitHub][2])

### 1.3 Behavior a generated test should distinguish

The key distinction is:

| Operation                    | BUGGY                                           | FIXED                         |
| ---------------------------- | ----------------------------------------------- | ----------------------------- |
| Create `FastDateFormat`      | Works                                           | Works                         |
| Format normally              | Works                                           | Works                         |
| Serialize formatter          | **Fails** because internal rules are serialized | **Passes**                    |
| Deserialize formatter        | Cannot be reached successfully                  | Passes                        |
| Format after deserialization | Cannot be reached                               | Produces same expected output |

Therefore, the strongest defect-oriented test is a **serialization round-trip test**.

### 1.4 Boundary / representative / regression cases

I would use:

* **Representative:** ordinary date pattern.
* **Representative:** pattern containing textual fields and time fields, exercising multiple internal `Rule` objects.
* **Boundary:** formatter with a minimal/simple pattern.
* **Regression:** verify normal formatting still works without serialization.
* **Regression:** verify formatter configuration such as timezone is preserved after round-trip.

Importantly, testing only `toString()` would not expose the defect from the supplied source because the `toString()` implementation itself is unchanged between the two versions.

## 3. JUNIT 4.12 TEST CODE

```java
package org.apache.commons.lang.time;

import static org.junit.Assert.assertEquals;

import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.util.Date;
import java.util.Locale;
import java.util.TimeZone;

import org.junit.Test;

public class FastDateFormatLang56Test {

    private FastDateFormat serializeAndDeserialize(FastDateFormat formatter)
            throws Exception {

        ByteArrayOutputStream byteOutput = new ByteArrayOutputStream();

        ObjectOutputStream output = new ObjectOutputStream(byteOutput);
        output.writeObject(formatter);
        output.close();

        ObjectInputStream input = new ObjectInputStream(
                new ByteArrayInputStream(byteOutput.toByteArray()));

        FastDateFormat restored = (FastDateFormat) input.readObject();
        input.close();

        return restored;
    }

    @Test
    public void testSerializeAndDeserializeDateFormatter()
            throws Exception {

        FastDateFormat formatter =
                FastDateFormat.getInstance("yyyy-MM-dd");

        Date date = new Date(1234567890000L);

        String before = formatter.format(date);

        FastDateFormat restored =
                serializeAndDeserialize(formatter);

        String after = restored.format(date);

        assertEquals(before, after);
    }

    @Test
    public void testSerializeFormatterWithTextAndTimeFields()
            throws Exception {

        FastDateFormat formatter =
                FastDateFormat.getInstance(
                        "EEEE, MMMM dd yyyy HH:mm:ss",
                        TimeZone.getTimeZone("GMT"),
                        Locale.US);

        Date date = new Date(1300000000000L);

        String before = formatter.format(date);

        FastDateFormat restored =
                serializeAndDeserialize(formatter);

        String after = restored.format(date);

        assertEquals(before, after);
    }

    @Test
    public void testSerializeFormatterWithTimezone()
            throws Exception {

        TimeZone zone = TimeZone.getTimeZone("GMT+07:00");

        FastDateFormat formatter =
                FastDateFormat.getInstance(
                        "yyyy/MM/dd HH:mm Z",
                        zone,
                        Locale.US);

        Date date = new Date(1357924680000L);

        String before = formatter.format(date);

        FastDateFormat restored =
                serializeAndDeserialize(formatter);

        String after = restored.format(date);

        assertEquals(before, after);
        assertEquals(zone, restored.getTimeZone());
    }

    @Test
    public void testSerializeFormatterWithLiteralPattern()
            throws Exception {

        FastDateFormat formatter =
                FastDateFormat.getInstance(
                        "yyyy-MM-dd 'at' HH:mm:ss",
                        TimeZone.getTimeZone("UTC"),
                        Locale.US);

        Date date = new Date(1400000000000L);

        String before = formatter.format(date);

        FastDateFormat restored =
                serializeAndDeserialize(formatter);

        String after = restored.format(date);

        assertEquals(before, after);
    }

    @Test
    public void testNormalFormattingStillWorks()
            throws Exception {

        FastDateFormat formatter =
                FastDateFormat.getInstance(
                        "MM/dd/yyyy",
                        TimeZone.getTimeZone("UTC"),
                        Locale.US);

        Date date = new Date(1500000000000L);

        String result = formatter.format(date);

        assertEquals("07/14/2017", result);
    }

    @Test
    public void testRoundTripPreservesFormattedResult()
            throws Exception {

        FastDateFormat formatter =
                FastDateFormat.getInstance(
                        "HH:mm:ss.SSS",
                        TimeZone.getTimeZone("GMT+05:30"),
                        Locale.US);

        Date date = new Date(1600000000123L);

        String expected = formatter.format(date);

        FastDateFormat restored =
                serializeAndDeserialize(formatter);

        assertEquals(expected, restored.format(date));
    }
}
```

## 4. DEFECT DETECTION STRATEGY

### Test 1 — Basic serialization

**BUGGY:**
`writeObject()` attempts to serialize `mRules`, whose contained rule objects are not serializable. The test should fail with a serialization-related exception, typically `NotSerializableException`.

**FIXED:**
`mRules` is transient, so serialization succeeds. During deserialization, `readObject()` calls `init()`, reconstructing the rules. The formatted result is unchanged.

**Defect-detecting:** **Yes**

---

### Test 2 — Text and time fields

This uses a pattern containing several different formatting components.

**BUGGY:** serialization fails because the internal rules are still part of the serialized state.

**FIXED:** serialization succeeds and `init()` reconstructs the transient rules.

**Defect-detecting:** **Yes**

---

### Test 3 — Explicit timezone

This checks that serialization works when the formatter has an explicitly configured timezone.

**BUGGY:** serialization fails before a usable deserialized formatter can be obtained.

**FIXED:** serialization/deserialization succeeds and the formatter continues using the configured timezone.

**Defect-detecting:** **Yes**

---

### Test 4 — Literal pattern

This exercises a formatter whose parsed rule set contains literal text as well as date/time rules.

**BUGGY:** serialization fails because `mRules` is serialized.

**FIXED:** transient rules are reconstructed after deserialization.

**Defect-detecting:** **Yes**

---

### Test 5 — Normal formatting regression

This does not serialize anything.

**BUGGY:** normal formatting works.

**FIXED:** normal formatting also works.

**Defect-detecting:** **No — regression test**

Its purpose is to ensure the generated suite does not accidentally require the LANG-303 fix for ordinary formatting.

---

### Test 6 — Round-trip formatted result

**BUGGY:** serialization fails, so the test fails before the final assertion.

**FIXED:** formatter is successfully reconstructed and produces the same formatted result.

**Defect-detecting:** **Yes**

## 5. SUMMARY

* **Root cause:** `FastDateFormat` stored its internal `Rule[] mRules` and related state as normal serializable fields. The rules themselves were not serializable.
* **Fix:** mark the internal state `transient` and rebuild it using `init()` after deserialization.
* **Targeted behavior:** successful serialization/deserialization of an initialized `FastDateFormat`, followed by correct formatting.
* **Generated tests:** **6**

  * 5 directly exercise serialization/round-trip behavior.
  * 1 is a normal-formatting regression test.
* The tests are independent of the supplied trigger because they:

  * do not invoke `testLang303`;
  * do not reproduce its parsing operation;
  * use different formatting patterns and dates;
  * use standard Java serialization directly rather than copying the trigger's serialization helper;
  * derive their expected behavior from the production-source defect.

The Apache release notes explicitly identify LANG-303 as the fix for `FastDateFormat.mRules` not being transient or serializable. ([Apache Commons][1])

## 6. LIMITATIONS

1. **The prompt's metadata says the modified method is `toString`, but the supplied source difference is in serialization fields (`mRules` and `mMaxLengthEstimate`).** The `toString()` implementation shown in the supplied sources does not provide a behavioral difference. Therefore, the tests target the actual source-level defect rather than the method-name metadata.

2. The exact exception produced by Java serialization is not asserted. This is intentional: the important contract is that serialization succeeds on the FIXED version, rather than depending on a particular exception implementation.

3. Serialization tests depend on the Java serialization mechanism available in the Defects4J environment.

4. The absolute formatted dates are deliberately not based on the trigger's date/input scenario. The tests use independent timestamps and formatting patterns to exercise the same underlying defect.
