## 1. SOURCE CODE ANALYSIS

The uploaded prompt identifies **Lang-1 / LANG-747**, affecting `org.apache.commons.lang3.math.NumberUtils.createNumber`. 

The source-level defect is in the handling of **hexadecimal numbers near the signed `int`/`long` boundaries**.

The buggy implementation determines the target type mainly from the **number of hexadecimal digits**:

```java
if (hexDigits > 16) {
    return createBigInteger(str);
}
if (hexDigits > 8) {
    return createLong(str);
}
return createInteger(str);
```

The problem is that digit count alone is insufficient for values with exactly **8 or 16 significant hexadecimal digits**.

For example, an 8-digit hexadecimal value beginning with `8`–`F` cannot be represented as a positive Java `Integer`, even though it has only 8 hex digits. Likewise, a 16-digit value beginning with `8`–`F` cannot be represented as a positive `Long`.

The fixed revision adds a scan that removes leading zeroes and records the first significant hexadecimal digit. It then changes the boundary checks to:

```java
hexDigits > 16 || (hexDigits == 16 && firstSigDigit > '7')
```

and:

```java
hexDigits > 8 || (hexDigits == 8 && firstSigDigit > '7')
```

The actual commit confirms these changes for LANG-747. ([GitHub][1])

The issue itself describes LANG-747 as `NumberUtils` not handling Long hexadecimal numbers correctly. ([Apache Issues][2])

### Important observation

The original Defects4J trigger contains particular boundary values such as `0x80000000`, `0xFFFFFFFF`, `0x8000000000000000`, etc. ([GitHub][1])

Therefore, the tests below deliberately use **different hexadecimal values** while exercising the same boundary conditions.

## 2. TEST CASE DESIGN

I would use **4 complementary tests**.

| Test | Input                  |        Significant hex digits | Expected type | Purpose                                            |
| ---- | ---------------------- | ----------------------------: | ------------- | -------------------------------------------------- |
| 1    | `0x81000000`           |                             8 | `Long`        | 8-digit value above signed `Integer.MAX_VALUE`     |
| 2    | `0xFEDCBA9876543210`   |                            16 | `BigInteger`  | 16-digit value above signed `Long.MAX_VALUE`       |
| 3    | `0x0000000081000000`   |  8 after leading-zero removal | `Long`        | Checks leading-zero normalization                  |
| 4    | `0x00FEDCBA9876543210` | 16 after leading-zero removal | `BigInteger`  | Checks leading-zero normalization at Long boundary |

These are independently derived from the fixed-source change: the fix specifically counts leading zeroes and examines the first significant digit before selecting `Integer`, `Long`, or `BigInteger`. ([GitHub][1])

The tests verify both:

* the **numeric value**
* the **actual returned Java type**

That is important because simply checking `.longValue()` could miss an incorrect type selection.

## 3. JUNIT 4.12 TEST CODE

Save this as `NumberUtilsTest.java`.

```java
package org.apache.commons.lang3.math;

import static org.junit.Assert.assertEquals;
import static org.junit.Assert.assertTrue;

import java.math.BigInteger;

import org.junit.Test;

public class NumberUtilsTest {

    @Test
    public void testCreateNumberEightDigitHexAboveIntegerRange() {
        Number result = NumberUtils.createNumber("0x81000000");

        assertTrue(result instanceof Long);
        assertEquals(Long.valueOf(0x81000000L), result);
    }

    @Test
    public void testCreateNumberSixteenDigitHexAboveLongRange() {
        Number result = NumberUtils.createNumber("0xFEDCBA9876543210");

        assertTrue(result instanceof BigInteger);
        assertEquals(
                new BigInteger("FEDCBA9876543210", 16),
                result);
    }

    @Test
    public void testCreateNumberEightDigitHexWithLeadingZeros() {
        Number result = NumberUtils.createNumber("0x0000000081000000");

        assertTrue(result instanceof Long);
        assertEquals(Long.valueOf(0x81000000L), result);
    }

    @Test
    public void testCreateNumberSixteenDigitHexWithLeadingZeros() {
        Number result = NumberUtils.createNumber("0x00FEDCBA9876543210");

        assertTrue(result instanceof BigInteger);
        assertEquals(
                new BigInteger("FEDCBA9876543210", 16),
                result);
    }
}
```

## 4. DEFECT DETECTION STRATEGY

### Test 1 — 8-digit hexadecimal above `Integer` range

**Input**

```text
0x81000000
```

It has exactly 8 significant hexadecimal digits and begins with `8`.

The value is larger than `Integer.MAX_VALUE`, so it needs a `Long`.

**Buggy version**

The old condition only checks:

```java
hexDigits > 8
```

Since `8 > 8` is false, the buggy implementation attempts to create an `Integer`.

That can result in `NumberFormatException` rather than returning the required `Long`.

**Fixed version**

The fixed condition additionally checks:

```java
hexDigits == 8 && firstSigDigit > '7'
```

Since the first significant digit is `8`, the implementation selects `Long`.

**Expected**

```text
Long
0x81000000
```

This directly targets the 8-digit signed-boundary defect.

---

### Test 2 — 16-digit hexadecimal above `Long` range

**Input**

```text
0xFEDCBA9876543210
```

There are exactly 16 significant hexadecimal digits, and the first digit is `F`.

Therefore the value is larger than `Long.MAX_VALUE`.

**Buggy version**

The old implementation only checks:

```java
hexDigits > 16
```

Sixteen is not greater than sixteen, so it does not promote directly to `BigInteger`.

It instead attempts the `Long` path.

**Fixed version**

The fixed implementation checks:

```java
hexDigits == 16 && firstSigDigit > '7'
```

`F > 7`, so it selects `BigInteger`.

**Expected**

```text
BigInteger
FEDCBA9876543210
```

---

### Test 3 — 8-digit value with leading zeroes

**Input**

```text
0x0000000081000000
```

The leading zeroes should not affect the actual magnitude.

After removing them, the significant part is:

```text
81000000
```

which contains 8 significant hexadecimal digits and begins with `8`.

The fixed source explicitly adds logic to strip leading zeroes before deciding which numeric type is appropriate. ([GitHub][1])

**Expected**

```text
Long
0x81000000
```

This checks that the fix does not work only for numbers written without leading zeroes.

---

### Test 4 — 16-digit value with leading zeroes

**Input**

```text
0x00FEDCBA9876543210
```

After removing the leading zeroes:

```text
FEDCBA9876543210
```

There are 16 significant digits and the first significant digit is `F`.

Therefore the expected type is `BigInteger`.

This specifically exercises the combination of:

```text
leading zero removal
+
16-digit boundary
+
first significant digit > 7
```

**Expected**

```text
BigInteger
FEDCBA9876543210
```

### Detection criterion

For each test, the experiment should classify it as defect-detecting **only if**:

```text
BUGGY VERSION = FAIL
FIXED VERSION = PASS
```

A failure on both versions does **not** count as detection.

The tests above are based on the actual source change in the LANG-747 fix, which added the first-significant-digit checks specifically at the 8- and 16-digit hexadecimal boundaries. ([GitHub][1])

## 5. SUMMARY

* **Defect:** `NumberUtils.createNumber()` incorrectly determines the numeric type of certain hexadecimal values.
* **Root cause:** the buggy implementation relies only on hexadecimal digit count.
* **8-digit boundary:** values beginning with `8`–`F` need `Long`, not `Integer`.
* **16-digit boundary:** values beginning with `8`–`F` need `BigInteger`, not `Long`.
* **Leading zeroes:** must be ignored when determining the significant digit count.
* **Tests generated:** 4.
* **Original trigger avoided:** none of the original trigger input values are used.
* **Assertions:** each test checks both the numeric value and the returned Java type.

The underlying LANG-747 issue specifically states that `createNumber()` did not properly handle larger hexadecimal values and that values beyond the 8-digit `Integer` range should be handled using `Long`. ([Apache Issues][2])
