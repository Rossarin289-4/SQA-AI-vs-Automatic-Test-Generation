## 1. The behavior that differs

The key source difference is inside `greatestCommonDivisor(int u, int v)`.

### BUGGY

```java
if (Math.abs(u) <= 1 || Math.abs(v) <= 1) {
    return 1;
}
```

### FIXED

```java
if (u == 0 || v == 0) {
    if (u == Integer.MIN_VALUE || v == Integer.MIN_VALUE) {
        throw new ArithmeticException("overflow: gcd is 2^31");
    }
    return Math.abs(u) + Math.abs(v);
}

if (Math.abs(u) == 1 || Math.abs(v) == 1) {
    return 1;
}
```

The important change is that the fixed version gives **zero operands an explicit GCD definition**, instead of treating `0` as if its GCD were always `1`.

The Apache issue for LANG-662 identifies the underlying problem as the `greatestCommonDivisor` implementation and specifically concerns extreme `Integer.MIN_VALUE` values. ([Apache Issues][1])

However, there is an important complication with the exact source supplied in the prompt:

* `getReducedFraction()` returns immediately when `numerator == 0`.
* `reduce()` returns immediately when `numerator == 0`.
* `multiplyBy()` returns immediately when either numerator is zero.
* `addSub()` returns immediately when either numerator is zero.
* `getReducedFraction()` rejects denominator `0`.

Therefore, the newly added `u == 0 || v == 0` branch of `greatestCommonDivisor()` appears to be **unreachable through the normal public `Fraction` API in the supplied source**.

This matters because the JIRA description says LANG-662 concerns `Integer.MIN_VALUE` with powers of two, while the supplied buggy/fixed method difference primarily adds zero handling. ([Apache Issues][1])

## 2. The likely root cause visible from the source

The original implementation assumes that zero has already been handled by callers:

```java
if (Math.abs(u) <= 1 || Math.abs(v) <= 1) {
    return 1;
}
```

That assumption is unsafe for a general GCD implementation because:

```text
gcd(0, n) = |n|
gcd(0, 1) = 1
gcd(0, 0) = 0
```

whereas the buggy shortcut returns `1` for every case involving zero.

The fixed implementation instead explicitly handles zero before the `abs == 1` optimization:

```java
if (u == 0 || v == 0) {
    ...
    return Math.abs(u) + Math.abs(v);
}
```

The fixed code also protects the special case where the non-zero operand is `Integer.MIN_VALUE`, because its positive absolute value cannot be represented by a Java `int`. The current Apache source retains this same structure. ([Apache Commons][2])

For LANG-662 specifically, Apache's issue record states that the defect was associated with calculating the GCD involving `Integer.MIN_VALUE` and powers of two. ([Apache Issues][1])

## 3. The specific behavior a generated test should distinguish

The ideal generated test should exercise a path where `greatestCommonDivisor()` receives a zero operand and therefore distinguishes:

```text
BUGGY: gcd(0, n) -> 1
FIXED: gcd(0, n) -> |n|
```

But with the **exact public source supplied here**, normal public methods prevent that situation from reaching `greatestCommonDivisor()`.

For example:

```java
Fraction.getReducedFraction(0, 8)
```

does **not** call `greatestCommonDivisor()`, because:

```java
if (numerator == 0) {
    return ZERO;
}
```

Similarly:

```java
Fraction.getFraction(0, 8).reduce()
```

does not reach the method.

So a test such as:

```java
assertEquals(0, ...);
```

would pass on both versions and would not detect the supplied defect.

The JIRA's documented LANG-662 behavior is the `Integer.MIN_VALUE` / power-of-two reduction scenario. ([Apache Issues][1])

## 5. Complete JUnit 4.12 test class

Because the supplied buggy/fixed implementations do not expose a public behavioral difference that these tests can reliably distinguish, the following suite deliberately tests the documented LANG-662 boundary behavior without pretending that every test is defect-detecting.

```java
package org.apache.commons.lang3.math;

import static org.junit.Assert.assertEquals;

import org.junit.Test;

public class FractionLang22Test {

    @Test
    public void testReducedFractionIntegerMinValueWithFour() {
        Fraction fraction = Fraction.getReducedFraction(Integer.MIN_VALUE, 4);

        assertEquals(Integer.MIN_VALUE / 4, fraction.getNumerator());
        assertEquals(1, fraction.getDenominator());
    }

    @Test
    public void testReducedFractionIntegerMinValueWithEight() {
        Fraction fraction = Fraction.getReducedFraction(Integer.MIN_VALUE, 8);

        assertEquals(Integer.MIN_VALUE / 8, fraction.getNumerator());
        assertEquals(1, fraction.getDenominator());
    }

    @Test
    public void testReduceIntegerMinValueWithFour() {
        Fraction fraction = Fraction.getFraction(Integer.MIN_VALUE, 4);
        Fraction reduced = fraction.reduce();

        assertEquals(Integer.MIN_VALUE / 4, reduced.getNumerator());
        assertEquals(1, reduced.getDenominator());
    }

    @Test
    public void testOrdinaryNegativeFractionReduction() {
        Fraction fraction = Fraction.getReducedFraction(-48, 12);

        assertEquals(-4, fraction.getNumerator());
        assertEquals(1, fraction.getDenominator());
    }

    @Test
    public void testOrdinaryPositiveFractionReduction() {
        Fraction fraction = Fraction.getReducedFraction(84, 28);

        assertEquals(3, fraction.getNumerator());
        assertEquals(1, fraction.getDenominator());
    }

    @Test
    public void testAlreadyReducedFractionRemainsUnchanged() {
        Fraction fraction = Fraction.getReducedFraction(7, 13);

        assertEquals(7, fraction.getNumerator());
        assertEquals(13, fraction.getDenominator());
    }

    @Test
    public void testZeroFractionIsNormalized() {
        Fraction fraction = Fraction.getReducedFraction(0, 19);

        assertEquals(0, fraction.getNumerator());
        assertEquals(1, fraction.getDenominator());
    }
}
```

### Summary

* **Root cause:** the fixed `greatestCommonDivisor()` explicitly handles zero operands instead of allowing the `abs <= 1` shortcut to classify zero as GCD `1`.
* **Documented LANG-662 behavior:** extreme `Integer.MIN_VALUE` numerator combined with a power-of-two denominator is the important boundary family. ([Apache Issues][1])
* **Generated tests:** 7 independent tests.
* **Independent from trigger:** the values use `/4` and `/8`, rather than reproducing the documented trigger's `/2` input.
* **However:** the supplied buggy implementation appears capable of producing the expected results for these `Integer.MIN_VALUE`/power-of-two cases, so these tests are regression tests rather than reliable defect detectors.

### Limitations / uncertainty

There is a **source-level inconsistency that prevents a trustworthy defect-detecting test from being derived from the prompt alone**.

The supplied fixed method changes:

```java
if (Math.abs(u) <= 1 || Math.abs(v) <= 1)
```

to:

```java
if (u == 0 || v == 0) {
    ...
}

if (Math.abs(u) == 1 || Math.abs(v) == 1)
```

But the public callers shown in the source already prevent zero from reaching `greatestCommonDivisor()`. Consequently, the added branch does not appear externally observable.

At the same time, the official LANG-662 issue describes the defect as failure to handle `Integer.MIN_VALUE` with `2^k`, and the issue records the original `/2` trigger behavior. ([Apache Issues][1])

Therefore, **I would not claim that an independently generated JUnit test detects Lang-22 from the supplied source comparison**. The safest experimental conclusion is to flag the mismatch and verify the actual checked-out `Lang-22-buggy` and `Lang-22-fixed` bytecode/source around `greatestCommonDivisor()` before counting a test as defect-detecting. The Apache source history confirms that the zero-handling change is part of the eventual implementation. ([Apache Commons][2])
