### Identify

1. **The behavior that differs:**  
   In `DurationFormatUtils.formatPeriod(...)`, when `days < 0` during the initial estimation reduction loop, the buggy version uses a hardcoded `days += 31;` adjustment (which fails for months with fewer or more than 31 days or varying calendar lengths). In contrast, the fixed version uses dynamic calendar arithmetic (`end.add(Calendar.MONTH, -1); days += end.getActualMaximum(Calendar.DAY_OF_MONTH); ... end.add(Calendar.MONTH, 1);`), correctly accounting for the actual days in the preceding month.

2. **The likely root cause visible from the source:**  
   The hardcoded addition of `31` days when normalizing negative day differences incorrectly shifts the period calculation for months with fewer than 31 days (such as February, April, June, September, November) or when crossing month boundaries, leading to incorrect day and month calculations in `formatPeriod`.

3. **The specific behavior that a generated test should distinguish between the buggy and fixed versions:**  
   A test measuring periods spanning across months with non-31-day lengths (e.g., from January 14th to February 14th, or similar spans involving February or 30-day months) will yield an incorrect number of days or months under the buggy version due to the fixed `31` offset, whereas the fixed version correctly computes the exact calendar duration.

4. **Boundary cases, representative cases, and regression cases that are independently designed:**  
   - *Case 1 (Non-31-day month transition / February span):* Measuring the exact period between dates spanning February where the fixed adjustment logic is required.
   - *Case 2 (30-day month boundary transition):* Spanning between a 31-day month and a 30-day month using patterns requesting days/months to verify correct subtraction/addition handling.
   - *Case 3 (Short duration period vs long duration boundary):* Ensuring correct normalization when `millis >= 28 * DateUtils.MILLIS_PER_DAY` triggers the calendar path instead of short duration paths.

import java.util.Calendar;
import java.util.TimeZone;
import static org.junit.Assert.assertEquals;

public class DurationFormatUtilsIndependentTest {

        );

### DEFECT DETECTION STRATEGY

- **BUGGY VERSION:**  
  - For `testFormatPeriodAcrossFebruary`, because `days < 0` or month-end correction relies on adding `31` rather than querying `end.getActualMaximum(Calendar.DAY_OF_MONTH)`, the calculated day/month offsets become misaligned when crossing months with fewer than 31 days.
  - Test assertions fail due to incorrect number of days/months returned.
- **FIXED VERSION:**  
  - Uses dynamic calendar operations (`end.add(Calendar.MONTH, -1)` and `end.getActualMaximum(Calendar.DAY_OF_MONTH)`), correctly calculating variable month lengths.
  - Tests pass successfully.

### SUMMARY

- **Root cause:** Hardcoded `days += 31;` in `formatPeriod` normalization loop for negative day difference, ignoring actual variable lengths of preceding months.
- **Targeted behavior:** Accurate period formatting (`formatPeriod`) across month boundaries with varying lengths (such as February and 30-day months).
- **Number of generated tests:** 3 distinct test methods.
- **Independence from original trigger test:** Designed entirely from first-principles analysis of the date/calendar normalization arithmetic discrepancy between the buggy and fixed code, without copying the exact inputs or structure of the JIRA test case.
