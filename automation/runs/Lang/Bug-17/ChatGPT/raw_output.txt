## 1. Behavior that differs

The defect is in the **character-position loop** of `CharSequenceTranslator.translate(CharSequence, Writer)`.

The buggy version calculates:

```java
int len = Character.codePointCount(input, 0, input.length());
```

but then uses `pos` as if it were a **UTF-16 character index**. Those are not interchangeable when the input contains supplementary Unicode characters, because a supplementary code point occupies **two `char` values** in a Java `String`.

The fixed version instead uses:

```java
int len = input.length();
```

and advances `pos` according to the number of UTF-16 characters consumed by each code point. The JIRA report for LANG-720 specifically identifies the incorrect loop counter as the cause of `StringEscapeUtils.escapeXml()` producing wrong results for supplementary-plane characters. ([Apache Issues][1])

So the important distinction is:

* **BUGGY:** can revisit the second `char` of a supplementary code point as though it were a separate character, or stop before processing the rest of the input.
* **FIXED:** processes supplementary code points using their correct UTF-16 width and continues through the entire input.

## 2. Likely root cause visible from the source

The root cause is a **code-point count vs. UTF-16 character-index mismatch**.

### Buggy

```java
int pos = 0;
int len = Character.codePointCount(input, 0, input.length());

while (pos < len) {
    ...
    pos++;
}
```

`len` counts Unicode **code points**, whereas `pos` is used with APIs such as:

```java
Character.codePointAt(input, pos)
```

which expect a UTF-16 `char` index.

For example, conceptually:

```text
supplementary character + "A"

UTF-16 chars:
[ high-surrogate ][ low-surrogate ][ A ]

length() = 3
codePointCount() = 2
```

The buggy implementation therefore treats the effective input length as `2` even though the character indices extend to `2`.

The fixed implementation uses:

```java
int len = input.length();
```

and increments `pos` by the actual UTF-16 width of the code point. This directly addresses the issue documented in LANG-720. ([Apache Issues][1])

## 3. Specific behavior the generated tests should distinguish

The tests should verify that **a supplementary Unicode code point followed by additional input is processed exactly once and that the following input is not lost or duplicated**.

I would use a small custom `CharSequenceTranslator` whose `translate(input, index, out)` returns `0`. This is useful here because it exercises the **modified final `translate(CharSequence, Writer)` algorithm directly**, without depending on a particular XML entity mapping.

The expected contract is simple:

> If the translator consumes nothing, the character/code point should be copied unchanged, and the complete input should remain unchanged.

The strongest defect-oriented pattern is therefore:

```text
supplementary code point + ordinary character
```

and

```text
supplementary code point + supplementary code point
```

These expose the mismatch between code-point count and UTF-16 indexing.

This is also consistent with the historical LANG-720 description: the defect specifically concerns supplementary-plane characters in `StringEscapeUtils.escapeXml()`. ([Apache Issues][1])

---

## 4. Boundary, representative, and regression cases

I would use **four tests**, with complementary purposes.

| Test | Input structure                                | Purpose                                                         |
| ---- | ---------------------------------------------- | --------------------------------------------------------------- |
| 1    | one supplementary code point + ASCII           | Minimal boundary case                                           |
| 2    | one supplementary code point + two ASCII chars | Ensures processing continues beyond the immediate next position |
| 3    | two supplementary code points                  | Exercises repeated surrogate-pair handling                      |
| 4    | ASCII + supplementary code point + ASCII       | Regression for supplementary character in the middle            |

The supplementary character can be constructed using `Character.toChars(...)`, rather than embedding a particular Unicode literal. This makes the intent explicit and avoids tying the test to the original trigger data.

A useful choice is code point `0x1F642` (🙂), which is outside the BMP and therefore represented by a surrogate pair in UTF-16.

### Why these are independent

None of these tests needs the original `StringEscapeUtilsTest::testLang720` implementation or its exact input/output pair. They are derived directly from the source-level invariant:

> **UTF-16 index movement must agree with `input.length()`, while supplementary code points may occupy two UTF-16 characters.**

## 5. Complete JUnit 4.12 test class

```java
package org.apache.commons.lang3.text.translate;

import static org.junit.Assert.assertEquals;

import org.junit.Test;

public class CharSequenceTranslatorLang17Test {

    private CharSequenceTranslator identityTranslator() {
        return new CharSequenceTranslator() {
            @Override
            public int translate(CharSequence input, int index,
                    java.io.Writer out) {
                return 0;
            }
        };
    }

    @Test
    public void testSupplementaryCharacterFollowedBySingleAsciiCharacter() {
        String supplementary = new String(Character.toChars(0x1F642));
        String input = supplementary + "A";

        String result = identityTranslator().translate(input);

        assertEquals(input, result);
    }

    @Test
    public void testSupplementaryCharacterFollowedByMultipleAsciiCharacters() {
        String supplementary = new String(Character.toChars(0x1F642));
        String input = supplementary + "XYZ";

        String result = identityTranslator().translate(input);

        assertEquals(input, result);
    }

    @Test
    public void testTwoConsecutiveSupplementaryCharacters() {
        String first = new String(Character.toChars(0x1F642));
        String second = new String(Character.toChars(0x1F680));
        String input = first + second;

        String result = identityTranslator().translate(input);

        assertEquals(input, result);
    }

    @Test
    public void testSupplementaryCharacterInMiddleOfAsciiText() {
        String supplementary = new String(Character.toChars(0x1F642));
        String input = "AB" + supplementary + "CD";

        String result = identityTranslator().translate(input);

        assertEquals(input, result);
    }
}
```

## 6. Defect detection strategy, summary, and limitations

### Detection strategy

#### Test 1 — supplementary + one ASCII

**Input shape:**

```text
[supplementary code point]A
```

**BUGGY VERSION:**
Expected to produce an incorrect result because `codePointCount()` is smaller than the UTF-16 `length()`. After processing the supplementary code point, the buggy loop can process its low surrogate again instead of advancing to `A`.

**FIXED VERSION:**
Returns exactly the original input.

**Detection:** BUGGY fails the `assertEquals`; FIXED passes.

---

#### Test 2 — supplementary + multiple ASCII

**Input shape:**

```text
[supplementary code point]XYZ
```

**BUGGY VERSION:**
The incorrect loop boundary causes the later characters to be processed incorrectly or omitted.

**FIXED VERSION:**
Returns the complete original string.

**Detection:** BUGGY fails; FIXED passes.

This is complementary to Test 1 because it checks that the problem is not merely a one-character boundary condition.

---

#### Test 3 — two supplementary characters

**Input shape:**

```text
[supplementary][supplementary]
```

Each code point occupies two UTF-16 `char`s.

**BUGGY VERSION:**
The loop's code-point-based `len` is substantially smaller than the UTF-16 index range, so the second half of the surrogate representation can be revisited/misprocessed.

**FIXED VERSION:**
Both supplementary code points are copied exactly once.

**Detection:** BUGGY fails; FIXED passes.

---

#### Test 4 — supplementary character in the middle

**Input shape:**

```text
AB[supplementary]CD
```

**BUGGY VERSION:**
The supplementary pair is encountered at a nonzero UTF-16 position while the loop boundary is still based on code-point count. This can cause the suffix to be processed incorrectly.

**FIXED VERSION:**
The complete string is preserved.

**Detection:** BUGGY fails; FIXED passes.

---

### Summary

* **Root cause:** the buggy implementation uses `Character.codePointCount()` as the loop bound while `pos` is a UTF-16 `char` index.
* **Targeted behavior:** correct iteration over supplementary Unicode code points.
* **Number of generated tests:** **4**.
* **Test design:** one minimal boundary case, one longer suffix case, one consecutive-supplementary case, and one middle-position regression case.
* **Independence:** the tests are derived from the source-level defect and do not reproduce the original trigger test's implementation, inputs, or expected values.
* **API tested:** the public `CharSequenceTranslator.translate(CharSequence)` path, which internally exercises the modified `translate(CharSequence, Writer)` implementation.

The historical Apache release notes also explicitly record LANG-720 as the fix for `StringEscapeUtils.escapeXml()` handling supplementary-plane characters. ([Apache Commons][2])

### Limitations

The supplied source is sufficient to identify the core defect, but the complete surrounding Defects4J test environment and the exact original `testLang720` implementation were not provided. Therefore, the tests intentionally avoid relying on any particular XML entity behavior.

One practical point is important: these tests use an **identity translator** to isolate `CharSequenceTranslator.translate` itself. That gives a cleaner defect oracle than relying on `StringEscapeUtils`, because the expected behavior is simply that an identity translation must return the exact original UTF-16 string. The test therefore targets the modified production method rather than another translator's mapping logic.
