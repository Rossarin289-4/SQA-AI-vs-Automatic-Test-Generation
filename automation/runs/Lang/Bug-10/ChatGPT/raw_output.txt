## 1. Behavior that differs

The defect is in how `FastDateParser.escapeRegex()` handles whitespace in literal parts of a date pattern.

In the **buggy version**, whitespace is treated specially:

```java
if(Character.isWhitespace(c)) {
    if(!wasWhite) {
        wasWhite = true;
        regex.append("\\s*+");
    }
    continue;
}
```

So **one whitespace character in the format becomes `\s*+`**, meaning **zero or more whitespace characters**.

For example, with the pattern:

```text
yyyy M
```

the buggy parser effectively allows:

```text
2003 2
2003  2
2003\t2
2003\n2
20032
```

The last four are not equivalent to a literal single space in a `SimpleDateFormat` pattern.

The **fixed version** removes this whitespace-collapsing logic and treats whitespace as an ordinary literal character.

This matches the Apache issue description: `FastDateParser` was treating a single whitespace in the pattern as any number of whitespace characters, allowing inputs that `SimpleDateFormat` would reject. ([Apache Issues][1])

## 2. Likely root cause visible from the source

The root cause is the additional whitespace normalization in the buggy `escapeRegex()`:

```java
if(Character.isWhitespace(c)) {
    if(!wasWhite) {
        wasWhite = true;
        regex.append("\\s*+");
    }
    continue;
}
```

This changes the semantics of the format pattern.

A literal space should be escaped/copied into the generated regex as a literal space. Instead, the buggy implementation converts it to:

```regex
\s*+
```

which means:

> zero or more whitespace characters.

The fixed implementation simply iterates over the characters and escapes only regex metacharacters. Therefore, a space remains a literal space.

## 3. Specific behavior the generated tests should distinguish

The strongest independent test strategy is to use a pattern containing **exactly one literal space** and then provide inputs where that space is:

1. Completely missing.
2. Replaced by a tab.
3. Replaced by a newline.
4. Correctly present as one space.

For example:

```text
Pattern: yyyy M
```

Expected semantics:

| Input     | Expected           |
| --------- | ------------------ |
| `2003 2`  | Parse successfully |
| `20032`   | Reject             |
| `2003\t2` | Reject             |
| `2003\n2` | Reject             |

On the buggy implementation, the `\s*+` generated by `escapeRegex()` allows the invalid whitespace forms.

On the fixed implementation, the generated regex requires the literal space.

This directly targets the changed behavior rather than testing unrelated date-parsing functionality.

## 4. Boundary cases, representative cases, and regression cases

### Boundary case 1 — zero whitespace

```text
Pattern: yyyy M
Input:   20032
```

This is the most important case because `\s*+` permits **zero** whitespace.

* BUGGY: parses successfully → test fails
* FIXED: throws `ParseException` → test passes

### Boundary case 2 — tab instead of space

```text
Pattern: yyyy M
Input:   2003\t2
```

`\s` includes tab characters.

* BUGGY: parses successfully → test fails
* FIXED: rejects → test passes

### Boundary case 3 — newline instead of space

```text
Pattern: yyyy M
Input:   2003\n2
```

`\s` also includes newline characters.

* BUGGY: parses successfully → test fails
* FIXED: rejects → test passes

### Regression case — correct literal space

```text
Pattern: yyyy M
Input:   2003 2
```

This verifies that fixing the bug does not break the legitimate case.

* BUGGY: parses successfully
* FIXED: parses successfully

This test is therefore a **regression/sanity test**, not by itself a defect-detecting test.

## 5. JUnit 4.12 test class

I would use `FastDateParser` directly because its constructor is `protected`, and placing the test in the same package gives normal package-level access without reflection.

The tests use `Assert.fail()` and `assertNotNull()` rather than manually throwing `AssertionError`.

```java
package org.apache.commons.lang3.time;

import static org.junit.Assert.assertNotNull;
import static org.junit.Assert.fail;

import java.text.ParseException;
import java.util.Locale;
import java.util.TimeZone;

import org.junit.Test;

public class FastDateParserLang10Test {

    private static final TimeZone UTC = TimeZone.getTimeZone("UTC");
    private static final Locale LOCALE = Locale.US;

    @Test
    public void testRejectsInputWithMissingLiteralSpace() throws Exception {
        FastDateParser parser = new FastDateParser("yyyy M", UTC, LOCALE);

        try {
            parser.parse("20032");
            fail("Expected ParseException when the literal space is missing");
        } catch (ParseException expected) {
            // Expected on the fixed implementation.
        }
    }

    @Test
    public void testRejectsInputWithTabInsteadOfLiteralSpace() throws Exception {
        FastDateParser parser = new FastDateParser("yyyy M", UTC, LOCALE);

        try {
            parser.parse("2003\t2");
            fail("Expected ParseException when a tab replaces the literal space");
        } catch (ParseException expected) {
            // Expected on the fixed implementation.
        }
    }

    @Test
    public void testRejectsInputWithNewlineInsteadOfLiteralSpace() throws Exception {
        FastDateParser parser = new FastDateParser("yyyy M", UTC, LOCALE);

        try {
            parser.parse("2003\n2");
            fail("Expected ParseException when a newline replaces the literal space");
        } catch (ParseException expected) {
            // Expected on the fixed implementation.
        }
    }

    @Test
    public void testAcceptsInputWithRequiredLiteralSpace() throws Exception {
        FastDateParser parser = new FastDateParser("yyyy M", UTC, LOCALE);

        assertNotNull(parser.parse("2003 2"));
    }
}
```

## 6. Defect detection strategy and summary

### Expected behavior

| Test                                               | BUGGY             | FIXED                       | Detects defect?     |
| -------------------------------------------------- | ----------------- | --------------------------- | ------------------- |
| `testRejectsInputWithMissingLiteralSpace`          | Parses → **FAIL** | `ParseException` → **PASS** | **Yes**             |
| `testRejectsInputWithTabInsteadOfLiteralSpace`     | Parses → **FAIL** | `ParseException` → **PASS** | **Yes**             |
| `testRejectsInputWithNewlineInsteadOfLiteralSpace` | Parses → **FAIL** | `ParseException` → **PASS** | **Yes**             |
| `testAcceptsInputWithRequiredLiteralSpace`         | Parses → **PASS** | Parses → **PASS**           | No; regression test |

### Root cause

The buggy `escapeRegex()` converts each run of whitespace into:

```regex
\s*+
```

instead of preserving the whitespace as a literal character.

### Targeted behavior

The tests verify that a literal whitespace character in a `FastDateParser` pattern is **required**, rather than being optional or replaceable by arbitrary whitespace.

### Number of generated tests

**4 tests total**

* 3 defect-focused tests
* 1 valid-input regression test

### Why these are independent from the original trigger

The tests are derived directly from the source-level difference in `escapeRegex()`. They use a different pattern and different input values from the supplied Defects4J trigger information. They do not reproduce the trigger implementation or rely on the original trigger tests.

They also cover three distinct manifestations of the same defect:

* whitespace omitted,
* whitespace changed to tab,
* whitespace changed to newline.

The Apache Jira report independently confirms that LANG-831 concerns `FastDateParser` accepting whitespace variations that should not be accepted. ([Apache Issues][1])

### Limitations / uncertainty

The supplied source is sufficient to identify the defect mechanism with high confidence. The main limitation is that the exact original test implementation and its expected values were intentionally not used. Therefore, the proposed tests are designed from the buggy/fixed source behavior rather than from the original trigger.

One additional consideration is that `FastDateParser.parse(String)` uses `Matcher.lookingAt()`, so this suite intentionally uses malformed **separator placement** rather than relying on trailing-input behavior. This keeps the tests focused on the modified `escapeRegex()` behavior.
