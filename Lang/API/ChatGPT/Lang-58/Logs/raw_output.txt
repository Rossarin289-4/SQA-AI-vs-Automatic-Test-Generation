## 1. SOURCE CODE ANALYSIS

### 1.1 Behavior that differs

The defect is in the `L`/`l` suffix branch of `NumberUtils.createNumber(String)`.

The buggy condition is effectively:

```java
dec == null
&& exp == null
&& isDigits(numeric.substring(1))
&& (numeric.charAt(0) == '-' || Character.isDigit(numeric.charAt(0)))
```

The problem is that it **always removes the first character** before calling `isDigits()`.

For a positive one-digit value such as `"0L"`:

```text
numeric = "0"
numeric.substring(1) = ""
```

`isDigits("")` is false, so the method rejects the value even though it is a valid `Long`.

The fixed condition instead distinguishes negative numbers from ordinary positive numbers:

```java
dec == null
&& exp == null
&& (numeric.charAt(0) == '-' && isDigits(numeric.substring(1))
    || isDigits(numeric))
```

Thus a positive numeric string is checked directly, while a negative number has its leading minus removed. The Apache JIRA report explicitly identifies this as the LANG-300 defect and states that one-digit long values were incorrectly rejected while values with leading zeroes could work. ([Apache Issues][1])

The historical fix is also documented in Commons Lang's release notes as:

> `NumberUtils.createNumber throws NumberFormatException for one digit long.`

and LANG-300 was fixed in the 2.3 release. ([Apache Commons][2])

### 1.2 Likely root cause

The root cause is the **incorrect validation of the numeric portion for a positive number**.

The buggy implementation assumes that the first character should always be skipped before checking digits. That is appropriate for a negative value where the first character is `'-'`, but not for a positive value.

The repair changes the logic so that:

* negative number → remove `-`, then check the remaining digits;
* positive number → check the complete numeric string.

This exact condition change is also shown in an independent analysis of the Lang-58 repair. ([Darkrsw][3])

### 1.3 Behavior the tests must distinguish

The key property is:

> A valid positive one-digit integer followed by `L` or `l` must be converted successfully to a `Long`, rather than throwing `NumberFormatException`.

The tests should therefore target:

| Input category                       | Example | Expected behavior |
| ------------------------------------ | ------- | ----------------- |
| Positive one-digit, uppercase suffix | `"0L"`  | `Long(0)`         |
| Positive one-digit, lowercase suffix | `"8l"`  | `Long(8)`         |
| Positive multi-digit long            | `"42L"` | `Long(42)`        |
| Negative one-digit long              | `"-7L"` | `Long(-7)`        |
| Leading-zero value                   | `"05L"` | `Long(5)`         |

The first two directly target the faulty branch. The latter cases are complementary regression cases.

Importantly, `"0L"` is used here as an independently selected boundary value rather than reproducing the reported examples of `"1l"` through `"9l"`. The JIRA report identifies the defect as applying to one-digit long values generally. ([Apache Issues][1])

## 2. TEST CASE DESIGN

I would use **5 tests**, with two primary defect-detection tests and three complementary regression tests.

### Test 1 — positive one-digit zero with `L`

```text
Input: "0L"
Expected: Long value 0
```

Why: `0` is the lower boundary of the non-negative integer domain and independently exercises the case where `numeric.substring(1)` becomes empty.

**Expected:** BUGGY fails with `NumberFormatException`; FIXED returns `Long(0)`.

### Test 2 — positive one-digit value with lowercase `l`

```text
Input: "8l"
Expected: Long value 8
```

Why: Tests the lowercase type qualifier and a non-zero one-digit positive value.

**Expected:** BUGGY fails; FIXED returns `Long(8)`.

### Test 3 — multi-digit positive long

```text
Input: "42L"
Expected: Long value 42
```

Why: The buggy implementation can successfully process multi-digit positive values because `numeric.substring(1)` still contains digits. This establishes that the generated test suite is specifically targeting the one-digit boundary rather than treating all `L` values as broken.

**Expected:** BUGGY passes; FIXED passes.

### Test 4 — negative one-digit long

```text
Input: "-7L"
Expected: Long value -7
```

Why: Negative values are handled differently by the buggy condition because removing the first character removes the minus sign and leaves a digit string.

**Expected:** BUGGY passes; FIXED passes.

### Test 5 — leading-zero long

```text
Input: "05L"
Expected: Long value 5
```

Why: The JIRA report specifically notes that values with a leading zero behaved differently from the one-digit case. This is a useful regression case showing that the test suite is not simply asserting that every short `L` value should fail or succeed indiscriminately. ([Apache Issues][1])

**Expected:** BUGGY passes; FIXED passes.

## 4. DEFECT DETECTION STRATEGY

| Test                                               | BUGGY VERSION           | FIXED VERSION | Defect-detecting? |
| -------------------------------------------------- | ----------------------- | ------------- | ----------------- |
| `testCreateNumberPositiveSingleDigitZeroLong`      | `NumberFormatException` | `Long(0)`     | **Yes**           |
| `testCreateNumberPositiveSingleDigitLowercaseLong` | `NumberFormatException` | `Long(8)`     | **Yes**           |
| `testCreateNumberPositiveMultiDigitLong`           | `Long(42)`              | `Long(42)`    | Regression        |
| `testCreateNumberNegativeSingleDigitLong`          | `Long(-7)`              | `Long(-7)`    | Regression        |
| `testCreateNumberLeadingZeroLong`                  | `Long(5)`               | `Long(5)`     | Regression        |

### Why the first two fail on BUGGY

For `"0L"`:

```text
numeric = "0"
numeric.substring(1) = ""
```

The buggy implementation checks the empty string with `isDigits()`, which returns false. Therefore the method reaches the `NumberFormatException` path.

For `"8l"` the same structural problem occurs:

```text
numeric = "8"
numeric.substring(1) = ""
```

So the buggy version again rejects a valid one-digit long.

The fixed implementation checks:

```text
isDigits(numeric)
```

for a positive value, so `"0"` and `"8"` are accepted and passed to `createLong()`. This matches the documented repair. 

### Why the other tests are useful

The multi-digit and negative cases act as **control/regression cases**.

They demonstrate that the defect is not simply "the `L` suffix does not work." The buggy implementation already handles cases where:

* removing the first digit still leaves digits, or
* removing the leading `-` leaves digits.

That distinction is important for a defect-oriented test suite.

## 5. SUMMARY

* **Root cause:** the buggy `createNumber()` validation always checks `numeric.substring(1)`, even for positive numbers. For a one-digit positive value this produces an empty string.
* **Targeted behavior:** valid positive one-digit integers with an `L`/`l` suffix must be converted to `Long`.
* **Generated tests:** **5**.
* **Direct defect-detecting tests:** **2**.
* **Regression/control tests:** **3**.
* The tests are independent of the original trigger because they use a different boundary value (`"0L"`) and independently selected representative cases rather than reproducing the reported `"1l"`–`"9l"` examples. The JIRA description confirms that the underlying defect concerns one-digit long values. ([Apache Issues][1])
* The repair's essential change is the conditional distinction between negative numbers, which need `substring(1)`, and positive numbers, which should be validated as-is. ([Orbilu][4])
