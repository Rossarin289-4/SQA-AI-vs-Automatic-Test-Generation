## 1. Behavior Difference

The important discrepancy is that the **buggy `ExtendedMessageFormat` does not override `equals(Object)` or `hashCode()`**, while the fixed version does.

The fixed implementation makes equality depend on three layers:

1. `MessageFormat` state via `super.equals(obj)`
2. The runtime class
3. `ExtendedMessageFormat`-specific state:

   * `toPattern`
   * `registry`

The fixed `hashCode()` likewise incorporates `registry` and `toPattern`. This matches the Apache release notes for LANG-636, which explicitly describe the issue as **“ExtendedMessageFormat doesn't override equals(Object)”**. ([Apache Commons][1])

One important inconsistency in the supplied source description is that `setFormatsByArgumentIndex()` itself is **unchanged** between the two versions. The actual behavioral change visible in the supplied BUGGY/FIXED source is the addition of `equals()` and `hashCode()`. Therefore, the tests below target that actual source-level difference rather than the unchanged setter.

---

## 2. Root Cause

The root cause is an **incomplete equality/hash-code implementation for a subclass with additional state**.

In the buggy version, `ExtendedMessageFormat` inherits `MessageFormat.equals()` and `MessageFormat.hashCode()`. Consequently, state belonging specifically to `ExtendedMessageFormat` is not incorporated.

The fixed version explicitly checks:

```text
getClass()
toPattern
registry
```

and its `hashCode()` incorporates `registry` and `toPattern`.

This is particularly important when two `ExtendedMessageFormat` instances have the same underlying `MessageFormat` state but different registries. The fixed implementation considers those objects different, whereas the buggy inherited implementation can consider them equal.

The Apache source for later versions preserves this design: `equals()` compares the subclass class, `toPattern`, and `registry`, while `hashCode()` incorporates `registry` and `toPattern`. ([Javadoc][2])

## 3. Targeted Behavior and Independently Designed Cases

The key oracle is:

> Two `ExtendedMessageFormat` objects with equivalent `MessageFormat` state but different `ExtendedMessageFormat` registry state must **not** be equal.

I would use **three complementary tests**.

### Test 1 — Same configuration should remain equal

Create two independently constructed instances with the same pattern and no registry.

**Expected:**

* BUGGY: `true`
* FIXED: `true`

This is a regression/baseline test. It ensures the defect-oriented suite does not incorrectly demand inequality from equivalent objects.

### Test 2 — Different registry state must affect equality

Create:

* one `ExtendedMessageFormat` with no registry
* another with an unused registry entry

Both use the same ordinary pattern, so the inherited `MessageFormat` state is effectively the same.

**Expected:**

* BUGGY: `true` — inherited equality does not account for the subclass registry
* FIXED: `false` — fixed equality compares `registry`

This is the primary defect-detecting test.

### Test 3 — Hash-based collections must respect the corrected equality

Put an instance with one registry configuration into a `HashSet`, then ask whether the set contains another instance with the same pattern but a different registry.

**Expected:**

* BUGGY: `true`
* FIXED: `false`

This is complementary to Test 2 because it exercises the **`equals()`/`hashCode()` contract through a normal Java collection**, rather than simply asserting `equals()` directly.

### Boundary / representative / regression coverage

| Case                                                | Purpose                                          |
| --------------------------------------------------- | ------------------------------------------------ |
| Same pattern + same null registry                   | Equal-object regression                          |
| Same pattern + null vs unused registry              | Core defect                                      |
| Same pattern + different registry through `HashSet` | Equality/hash-code integration                   |
| Ordinary pattern without custom formatting          | Isolates equality state from formatting behavior |
| Different independently created instances           | Avoids identity (`==`) masking the defect        |

The tests deliberately do **not** invoke or reproduce `testEqualsHashcode`, and they do not use its exact inputs or expected values.

## 4. Complete JUnit 4.12 Test Class

```java
package org.apache.commons.lang3.text;

import static org.junit.Assert.assertFalse;
import static org.junit.Assert.assertTrue;

import java.util.Collections;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

import org.junit.Test;

public class ExtendedMessageFormatLang23Test {

    @Test
    public void testEquivalentFormatsRemainEqual() {
        ExtendedMessageFormat first =
                new ExtendedMessageFormat("Record: {0}");
        ExtendedMessageFormat second =
                new ExtendedMessageFormat("Record: {0}");

        assertTrue(first.equals(second));
        assertTrue(second.equals(first));
    }

    @Test
    public void testDifferentRegistryStateMakesFormatsUnequal() {
        ExtendedMessageFormat withoutRegistry =
                new ExtendedMessageFormat("Record: {0}");

        Map<String, FormatFactory> registry =
                Collections.singletonMap(
                        "unused",
                        new FormatFactory() {
                            @Override
                            public java.text.Format getFormat(
                                    String name,
                                    String arguments,
                                    java.util.Locale locale) {
                                return null;
                            }
                        });

        ExtendedMessageFormat withRegistry =
                new ExtendedMessageFormat("Record: {0}", registry);

        assertFalse(withoutRegistry.equals(withRegistry));
        assertFalse(withRegistry.equals(withoutRegistry));
    }

    @Test
    public void testDifferentRegistryStateIsRespectedByHashSet() {
        ExtendedMessageFormat withoutRegistry =
                new ExtendedMessageFormat("Entry: {0}");

        Map<String, FormatFactory> registry =
                Collections.singletonMap(
                        "notUsed",
                        new FormatFactory() {
                            @Override
                            public java.text.Format getFormat(
                                    String name,
                                    String arguments,
                                    java.util.Locale locale) {
                                return null;
                            }
                        });

        ExtendedMessageFormat withRegistry =
                new ExtendedMessageFormat("Entry: {0}", registry);

        Set<ExtendedMessageFormat> formats =
                new HashSet<ExtendedMessageFormat>();

        formats.add(withoutRegistry);

        assertFalse(formats.contains(withRegistry));
    }
}
```

## 5. BUGGY/FIXED Detection Strategy

### `testEquivalentFormatsRemainEqual`

**BUGGY VERSION**

* Both objects have the same pattern.
* Both have `registry == null`.
* Inherited `MessageFormat.equals()` sees equivalent state.
* **Expected: PASS (`true`)**

**FIXED VERSION**

* `super.equals()` succeeds.
* Same class.
* Same `toPattern`.
* Both registries are `null`.
* **Expected: PASS (`true`)**

This is a regression test, not the primary detector.

---

### `testDifferentRegistryStateMakesFormatsUnequal`

**BUGGY VERSION**

The two objects have the same effective `MessageFormat` state, but the second object has a registry. The buggy class does not compare its own `registry` field.

Therefore:

```text
withoutRegistry.equals(withRegistry)
```

is expected to return **`true`**.

The test requires `false`, so:

**Expected: FAIL**

**FIXED VERSION**

The fixed implementation reaches:

```text
if (ObjectUtils.notEqual(registry, rhs.registry)) {
    return false;
}
```

The registries differ (`null` versus a non-null map), so:

**Expected: PASS**

This is a direct defect-detecting test.

---

### `testDifferentRegistryStateIsRespectedByHashSet`

**BUGGY VERSION**

The buggy class inherits both equality and hash code from `MessageFormat`.

The two objects have the same inherited `MessageFormat` state, so their inherited hash codes are compatible with the inherited equality result.

Consequently, after inserting `withoutRegistry`, the set is expected to report:

```text
formats.contains(withRegistry) == true
```

But the test requires `false`.

**Expected: FAIL**

**FIXED VERSION**

The fixed `equals()` says the objects are different because their registries differ.

Therefore `HashSet.contains()` must not find `withRegistry` as the previously inserted object.

**Expected: PASS**

This test is useful because it validates the behavior through a standard collection rather than directly duplicating the equality assertion.

## 6. Summary and Limitations

### Summary

* **Root cause:** `ExtendedMessageFormat` inherited `MessageFormat.equals()`/`hashCode()` and therefore failed to include its own state.
* **Targeted behavior:** `registry` and `toPattern` must participate in equality, and corresponding hash-code behavior must support normal hash-based collections.
* **Generated tests:** **3**

  1. Equivalent objects remain equal.
  2. Different registry configurations are unequal.
  3. Different registry configurations are distinguished by `HashSet`.
* **Independence:** The suite does not call the supplied trigger test, does not reproduce its implementation, and uses independently chosen patterns and registry configurations. The tests are derived from the actual production-code difference.
* **Primary defect detector:** `testDifferentRegistryStateMakesFormatsUnequal`.

The documented Apache release information independently identifies LANG-636 as the fix for `ExtendedMessageFormat` not overriding `equals(Object)`. ([Apache Commons][1])

### Limitations

The supplied source shows `setFormatsByArgumentIndex()` unchanged between BUGGY and FIXED. Therefore, there is no source-level basis for designing a test specifically around a changed implementation of that method. The actual observable modification in the provided code is the addition of `equals()` and `hashCode()`, so the suite targets that behavior.

I have not executed these tests against the two local workspaces, so the BUGGY/FIXED outcomes are based on the supplied source comparison and the documented LANG-636 behavior rather than a local Defects4J execution. Defects4J itself defines a triggering test as one that fails on the buggy revision and passes on the fixed revision. ([defects4j.org][3])
