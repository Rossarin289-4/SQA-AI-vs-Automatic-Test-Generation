## 1. Behavior that differs

`LANG-607` is specifically about `StringUtils` methods incorrectly handling Unicode supplementary characters. The Apache commit for the fix shows that `indexOfAny(CharSequence, char[])` changed from treating **any matching UTF-16 `char` as a match** to checking whether a high-surrogate is followed by the correct low-surrogate. ([GitHub][1])

### BUGGY behavior

The buggy implementation effectively does:

```java
if (searchChars[j] == ch) {
    return i;
}
```

Therefore, if the input contains a supplementary character represented by:

```text
high-surrogate + low-surrogate
```

and only the **high-surrogate** matches the search array, the buggy implementation reports a match even when the following low-surrogate is different.

### FIXED behavior

The fixed implementation checks a surrogate pair together:

```java
if (i < csLast && j < searchLast && Character.isHighSurrogate(ch)) {
    if (searchChars[j + 1] == cs.charAt(i + 1)) {
        return i;
    }
} else {
    return i;
}
```

So a high-surrogate is considered a supplementary-character match only when its corresponding low-surrogate also matches. This is consistent with the fix commit for LANG-607. ([GitHub][1])

## 2. Likely root cause visible from the source

The root cause is **matching UTF-16 code units independently instead of treating a supplementary Unicode character as a surrogate pair**.

For example, suppose the input contains:

```text
A [high-surrogate][low-surrogate] B
```

The buggy implementation sees the high-surrogate and immediately returns its index if that `char` occurs in `searchChars`.

That is incorrect when the search array contains:

```text
[high-surrogate][different-low-surrogate]
```

because the complete Unicode character is different.

The fixed implementation adds the necessary pair comparison. The actual LANG-607 commit explicitly changes `indexOfAny` in this way. ([GitHub][1])

## 3. Specific behavior the generated test should distinguish

The most direct defect oracle is:

> **A supplementary character must not match when only its high-surrogate matches but its low-surrogate does not.**

The tests should therefore construct supplementary characters programmatically with `Character.toChars(...)`. This makes the test independent of particular emoji glyphs and avoids reproducing the trigger inputs.

For example:

```text
input:
"A" + supplementary-character-U+1F600 + "B"

search:
high-surrogate(U+1F600)
low-surrogate(of a different supplementary character)
```

The expected result is:

```text
FIXED = -1
BUGGY = 1
```

because the actual supplementary character starts at UTF-16 index `1`, but the complete surrogate pair is not present in the search array.

This targets the actual source-level defect rather than merely testing `containsAny` or another method that happens to depend on `indexOfAny`.

## 4. Boundary, representative, and regression cases

I would use **4 tests**.

| Test                                                                          | Purpose                                             |          BUGGY |         FIXED |
| ----------------------------------------------------------------------------- | --------------------------------------------------- | -------------: | ------------: |
| Mismatched low-surrogate after matching high-surrogate                        | Core false-positive defect                          |            `1` |          `-1` |
| Same mismatch with several ordinary search chars                              | Ensures search-array iteration does not mask defect |            `2` |          `-1` |
| Correct supplementary pair                                                    | Positive regression case                            |  correct index | correct index |
| Supplementary character after ordinary characters with unrelated search chars | Position/regression coverage                        | false positive |          `-1` |

The important distinction is that the first, second, and fourth tests use a **valid supplementary character in the input but an invalid/mismatched surrogate pair in the search set**.

The positive case ensures the test suite does not merely demand that supplementary characters never match.

Apache's documented behavior for `indexOfAny` is to return the index of a matching character and `-1` when there is no match; the LANG-607 fix specifically extends the matching logic to handle supplementary characters correctly. ([GitHub][2])

## 5. Complete JUnit 4.12 test class

```java
package org.apache.commons.lang3;

import static org.junit.Assert.assertEquals;

import org.junit.Test;

public class StringUtilsLang30Test {

    @Test
    public void testIndexOfAnyDoesNotMatchHighSurrogateWithWrongLowSurrogate() {
        String actualCharacter = new String(Character.toChars(0x1F600));
        String differentCharacter = new String(Character.toChars(0x1F601));

        char[] searchChars = {
            actualCharacter.charAt(0),
            differentCharacter.charAt(1)
        };

        assertEquals(-1, StringUtils.indexOfAny("A" + actualCharacter + "B", searchChars));
    }

    @Test
    public void testIndexOfAnyDoesNotAcceptPartialSupplementaryCharacterAmongOtherSearchChars() {
        String actualCharacter = new String(Character.toChars(0x1F680));
        String differentCharacter = new String(Character.toChars(0x1F681));

        char[] searchChars = {
            'x',
            actualCharacter.charAt(0),
            differentCharacter.charAt(1),
            'y'
        };

        assertEquals(-1, StringUtils.indexOfAny("ab" + actualCharacter + "cd", searchChars));
    }

    @Test
    public void testIndexOfAnyMatchesCompleteSupplementaryCharacter() {
        String target = new String(Character.toChars(0x1F642));

        char[] searchChars = {
            target.charAt(0),
            target.charAt(1)
        };

        assertEquals(2, StringUtils.indexOfAny("xy" + target + "z", searchChars));
    }

    @Test
    public void testIndexOfAnyRejectsMismatchedSupplementaryCharacterAtLaterPosition() {
        String actualCharacter = new String(Character.toChars(0x1F680));
        String differentCharacter = new String(Character.toChars(0x1F682));

        char[] searchChars = {
            'q',
            'r',
            actualCharacter.charAt(0),
            differentCharacter.charAt(1)
        };

        assertEquals(-1, StringUtils.indexOfAny("hello" + actualCharacter, searchChars));
    }
}
```

## 6. Defect detection strategy + summary

### Test 1 — mismatched surrogate pair

Input contains one supplementary character, but the search array contains its high-surrogate followed by the low-surrogate from a **different** supplementary character.

**BUGGY:**

```text
returns 1
```

The buggy code sees the matching high-surrogate and immediately returns its index.

**FIXED:**

```text
returns -1
```

The fixed code sees that the following low-surrogate does not match and therefore does not report a match.

**Defect-detecting: YES**

---

### Test 2 — mismatch among multiple search characters

The same semantic defect is tested with unrelated search characters before and after the surrogate components.

**BUGGY:**

```text
returns 2
```

**FIXED:**

```text
returns -1
```

This verifies that the defect is not dependent on the surrogate being the first search element.

**Defect-detecting: YES**

---

### Test 3 — complete supplementary character

The input and search array contain the **same complete surrogate pair**.

**BUGGY:**

```text
returns 2
```

**FIXED:**

```text
returns 2
```

This is a positive regression test confirming that valid supplementary-character matching continues to work after the fix.

**Defect-detecting: NO by itself**, but useful as a complementary regression test.

---

### Test 4 — mismatch at a later position

The supplementary character occurs after ordinary text, while the search array contains its high-surrogate paired with an unrelated low-surrogate.

**BUGGY:**

```text
returns 5
```

**FIXED:**

```text
returns -1
```

This provides additional positional coverage while targeting the same underlying surrogate-pair defect.

**Defect-detecting: YES**

### Overall

* **Generated tests:** 4
* **Directly defect-detecting:** 3
* **Positive regression:** 1
* **Modified method:** `StringUtils.indexOfAny`
* **Targeted defect:** false matching of a supplementary character based only on its high-surrogate
* **Expected oracle:** mismatched surrogate pair → `-1`

The tests are independent of the supplied trigger tests: they use different Unicode code points, construct the surrogate pairs independently with `Character.toChars`, and test the source-level invariant rather than copying the trigger implementation or its exact values. The LANG-607 commit confirms that the production fix specifically introduced supplementary-character pair checking in `indexOfAny`. ([GitHub][1])

### Limitations

The supplied source excerpt is truncated, so the exact buggy method body was not included in full in the prompt. However, the fixed revision can be inspected directly: its diff shows the old implementation returned immediately on a single matching `char`, while the fixed implementation checks a high-surrogate together with the following low-surrogate. ([GitHub][1])

Therefore, the three negative tests above are tightly derived from the actual LANG-607 source change rather than from the trigger test.
