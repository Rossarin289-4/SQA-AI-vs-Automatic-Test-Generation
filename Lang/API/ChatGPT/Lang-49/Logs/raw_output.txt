## 1. The behavior that differs

The defect is in `Fraction.reduce()` when the fraction has a **zero numerator but a denominator other than 1**.

The fixed revision adds an explicit zero-numerator case:

```java
if (numerator == 0) {
    return equals(ZERO) ? this : ZERO;
}
```

The buggy implementation goes directly to:

```java
int gcd = greatestCommonDivisor(Math.abs(numerator), denominator);
if (gcd == 1) {
    return this;
}
```

For a fraction such as `0/8`, the GCD helper immediately returns `1` because `abs(0) <= 1`. Therefore the buggy `reduce()` returns the original `0/8` instead of canonicalizing it to `Fraction.ZERO` (`0/1`).

The LANG-380 release note describes the issue as an infinite-loop problem in `Fraction.reduce()` when the numerator is zero. ([Apache Git Repositories][1]) However, the actual fixed commit shows that the concrete repair was the three-line zero-numerator guard above. ([GitHub][2])

---

## 2. The likely root cause visible from the source

The root cause is that `reduce()` assumes the normal GCD-based reduction path is sufficient for every fraction.

For zero:

* `numerator = 0`
* `Math.abs(numerator) = 0`
* `greatestCommonDivisor(0, denominator)` returns `1`
* `gcd == 1`
* buggy method returns `this`

So a non-canonical zero such as:

```text
0/8
```

remains:

```text
0/8
```

instead of being normalized to:

```text
0/1
```

The fixed code handles zero **before** calculating the GCD and returns the canonical `Fraction.ZERO` when necessary. The commit confirms that this was the actual production change for LANG-380. ([GitHub][2])

## 3. The specific behavior a generated test should distinguish

The main distinguishing behavior should be:

> Calling `reduce()` on a zero-valued fraction whose denominator is greater than 1 must return `Fraction.ZERO`, with numerator `0` and denominator `1`.

For example, independently chosen:

```text
Fraction.getFraction(0, 8).reduce()
```

Expected:

```text
numerator   = 0
denominator = 1
```

and ideally:

```java
assertSame(Fraction.ZERO, result);
```

### Important distinction

A zero fraction with denominator `1` is not useful as the main defect test because it is already canonical. The interesting case is:

```text
0/x where x != 1
```

The generated tests therefore focus on **unreduced zero fractions**, while ordinary non-zero fractions are used as regression controls.

## 5. Complete JUnit 4.12 test class

```java
package org.apache.commons.lang.math;

import static org.junit.Assert.assertEquals;
import static org.junit.Assert.assertSame;

import org.junit.Test;

public class FractionLang49Test {

    @Test
    public void testReduceZeroWithEvenDenominator() {
        Fraction fraction = Fraction.getFraction(0, 8);

        Fraction result = fraction.reduce();

        assertEquals(0, result.getNumerator());
        assertEquals(1, result.getDenominator());
        assertSame(Fraction.ZERO, result);
    }

    @Test
    public void testReduceZeroWithOddDenominator() {
        Fraction fraction = Fraction.getFraction(0, 9);

        Fraction result = fraction.reduce();

        assertEquals(0, result.getNumerator());
        assertEquals(1, result.getDenominator());
        assertSame(Fraction.ZERO, result);
    }

    @Test
    public void testReduceAlreadyCanonicalZero() {
        Fraction fraction = Fraction.ZERO;

        Fraction result = fraction.reduce();

        assertEquals(0, result.getNumerator());
        assertEquals(1, result.getDenominator());
        assertSame(fraction, result);
    }

    @Test
    public void testReduceNonZeroReducibleFraction() {
        Fraction fraction = Fraction.getFraction(18, 24);

        Fraction result = fraction.reduce();

        assertEquals(3, result.getNumerator());
        assertEquals(4, result.getDenominator());
    }

    @Test
    public void testReduceAlreadyReducedFraction() {
        Fraction fraction = Fraction.getFraction(5, 7);

        Fraction result = fraction.reduce();

        assertEquals(5, result.getNumerator());
        assertEquals(7, result.getDenominator());
        assertSame(fraction, result);
    }

    @Test
    public void testReduceNegativeReducibleFraction() {
        Fraction fraction = Fraction.getFraction(-12, 18);

        Fraction result = fraction.reduce();

        assertEquals(-2, result.getNumerator());
        assertEquals(3, result.getDenominator());
    }
}
```

## 6. Defect detection strategy

### Expected behavior

| Test                                  | BUGGY VERSION        | FIXED VERSION                   | Detects defect? |
| ------------------------------------- | -------------------- | ------------------------------- | --------------- |
| `testReduceZeroWithEvenDenominator`   | Returns `0/8`        | Returns `0/1` (`Fraction.ZERO`) | **YES**         |
| `testReduceZeroWithOddDenominator`    | Returns `0/9`        | Returns `0/1` (`Fraction.ZERO`) | **YES**         |
| `testReduceAlreadyCanonicalZero`      | Returns same `0/1`   | Returns same `0/1`              | No              |
| `testReduceNonZeroReducibleFraction`  | `3/4`                | `3/4`                           | No              |
| `testReduceAlreadyReducedFraction`    | `5/7`, same instance | `5/7`, same instance            | No              |
| `testReduceNegativeReducibleFraction` | `-2/3`               | `-2/3`                          | No              |

### How the defect is exposed

For:

```java
Fraction.getFraction(0, 8).reduce()
```

**BUGGY:**

```text
result = 0/8
```

The GCD path sees zero and returns `1`, so the method incorrectly treats the fraction as already reduced.

**FIXED:**

```text
result = 0/1
result == Fraction.ZERO
```

The new zero-specific branch executes before the GCD calculation.

Therefore the first two tests are direct defect-detecting tests.

### Summary

* **Root cause:** `reduce()` lacked an explicit zero-numerator normalization case.
* **Targeted behavior:** every zero-valued fraction should reduce to the canonical `Fraction.ZERO`, except that `0/1` can simply return itself.
* **Generated tests:** **6**
* **Defect-detecting tests:** **2**
* **Regression/control tests:** **4**
* **Independence:** the tests use independently selected denominators (`8` and `9`) and separately exercise canonical zero, normal reduction, already-reduced values, and negative values. They do not reproduce the supplied trigger implementation or its exact inputs.

### Limitations

The supplied source excerpt was truncated around `reduce()`, so the exact buggy method body was not fully visible in the prompt. I verified the historical fixed commit: it adds exactly the zero-numerator guard to `reduce()`, while the parent revision lacks it. ([GitHub][2])

One subtlety is that the LANG-380 issue description calls this an “infinite loop,” while the historical source comparison directly shows the observable correction as **zero normalization**. ([Apache Git Repositories][1]) For this reason, the generated tests assert the concrete API result rather than relying on a timeout-based test. This is also more stable for a JUnit 4.12/Defects4J experiment.
