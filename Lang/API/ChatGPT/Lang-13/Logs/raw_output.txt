## 1. Behavior Difference

The defect in **Lang-13 / LANG-788** is in `ClassLoaderAwareObjectInputStream.resolveClass()` used internally by `SerializationUtils.deserialize()`.

The buggy implementation tries to resolve a serialized class name using:

```java
Class.forName(name, false, classLoader)
```

and then:

```java
Class.forName(name, false,
        Thread.currentThread().getContextClassLoader())
```

If both attempts fail, the buggy version immediately propagates `ClassNotFoundException`.

The fixed implementation adds a final fallback:

```java
Class<?> cls = primitiveTypes.get(name);
if (cls != null)
    return cls;
else
    throw cnfe;
```

The new `primitiveTypes` map contains names such as:

```text
byte
short
int
long
float
double
boolean
char
void
```

This matters because primitive classes such as `long.class` are represented by their primitive names during Java serialization. `Class.forName("long", ...)` does **not** resolve `long.class`, so the buggy implementation eventually throws `ClassNotFoundException`.

The Apache issue confirms that LANG-788 concerns `SerializationUtils` failing when cloning primitive classes, and specifically identifies the missing primitive-class fallback in the custom `ObjectInputStream`. ([Apache Issues][1])

---

## 2. Likely Root Cause

The root cause is that `SerializationUtils` overrides `ObjectInputStream.resolveClass()` but does not preserve the JDK's primitive-class resolution behavior.

### Buggy flow

For a primitive class such as `long.class`:

```text
serialize(long.class)
        ↓
serialized class information contains "long"
        ↓
deserialize(...)
        ↓
resolveClass("long")
        ↓
Class.forName("long", ...)
        ↓
ClassNotFoundException
        ↓
context ClassLoader also fails
        ↓
ClassNotFoundException propagated
```

### Fixed flow

The fixed version adds:

```text
Class.forName(...) fails
        ↓
context ClassLoader fails
        ↓
lookup "long" in primitiveTypes
        ↓
long.class
```

The fix therefore restores primitive-class resolution that was lost when Commons Lang introduced its custom class-loader-aware `ObjectInputStream`. The later Apache implementation similarly uses a primitive-class lookup after the two class-loader attempts fail. ([Apache Commons][2])

## 3. Target Behavior and Independent Test Design

The generated tests should distinguish:

> **Deserializing a serialized primitive `Class` object should return the same primitive `Class` object rather than throwing `ClassNotFoundException`.**

I would test this through the normal public API:

```java
SerializationUtils.deserialize(
    SerializationUtils.serialize(long.class)
);
```

This directly exercises the modified `deserialize()` path without invoking the supplied trigger test.

### Independently selected cases

| Test | Input           | Expected behavior                            | Purpose                                                  |
| ---- | --------------- | -------------------------------------------- | -------------------------------------------------------- |
| 1    | `long.class`    | Deserializes successfully to `long.class`    | Main defect test                                         |
| 2    | `boolean.class` | Deserializes successfully to `boolean.class` | Different primitive-name path                            |
| 3    | `void.class`    | Deserializes successfully to `void.class`    | Tests another entry in primitive map                     |
| 4    | `long[].class`  | Deserializes successfully to `long[].class`  | Regression: array descriptor should still work           |
| 5    | `Integer.class` | Deserializes successfully to `Integer.class` | Regression: ordinary reference classes remain unaffected |

The supplied trigger is based on `int.class`. I intentionally do **not** use `int.class`; the main tests use `long.class`, `boolean.class`, and `void.class` instead.

The primitive cases are not random edge cases: they are directly derived from the missing `primitiveTypes` lookup in the fixed source.

## 5. Defect Detection Strategy

### `testDeserializeLongPrimitiveClass`

**BUGGY VERSION**

`long.class` is serialized and then passed through `deserialize()`.

During class resolution:

```text
"long"
    ↓
Class.forName("long", ...)
    ↓
ClassNotFoundException
```

The context class loader attempt also fails.

The buggy implementation has no primitive fallback, so the test throws `SerializationException` caused by `ClassNotFoundException`.

**Result: FAIL**

**FIXED VERSION**

The fixed implementation reaches:

```java
primitiveTypes.get("long")
```

and obtains:

```java
long.class
```

Therefore:

```java
assertSame(long.class, result);
```

passes.

**Result: PASS**

**Defect-detecting: YES**

---

### `testDeserializeBooleanPrimitiveClass`

**BUGGY VERSION**

`boolean.class` produces the primitive name `"boolean"`.

The buggy resolver cannot resolve that name with `Class.forName()`, so deserialization fails.

**Result: FAIL**

**FIXED VERSION**

The primitive map contains:

```java
primitiveTypes.put("boolean", boolean.class);
```

so the correct `Class` object is returned.

**Result: PASS**

**Defect-detecting: YES**

---

### `testDeserializeVoidPrimitiveClass`

**BUGGY VERSION**

The serialized class name is `"void"`.

The buggy implementation has no `"void"` fallback and therefore fails with a `SerializationException`.

**Result: FAIL**

**FIXED VERSION**

The fixed map contains:

```java
primitiveTypes.put("void", void.class);
```

so:

```java
assertSame(void.class, result);
```

passes.

**Result: PASS**

**Defect-detecting: YES**

---

### `testDeserializePrimitiveArrayClass`

**BUGGY VERSION**

A primitive array such as `long[].class` has a JVM array descriptor such as:

```text
[J
```

This is different from the primitive name `"long"`.

`Class.forName("[J", ...)` can resolve the array class, so the buggy implementation does not require the new primitive fallback.

**Result: PASS**

**FIXED VERSION**

The same array class resolves normally.

**Result: PASS**

**Defect-detecting: NO — regression test**

---

### `testDeserializeReferenceClass`

**BUGGY VERSION**

`Integer.class` is an ordinary reference class and can be resolved through:

```java
Class.forName("java.lang.Integer", ...)
```

so the primitive fallback is not required.

**Result: PASS**

**FIXED VERSION**

The same normal class-loading path succeeds.

**Result: PASS**

**Defect-detecting: NO — regression test**

## 6. Summary and Limitations

### Summary

* **Root cause:** the custom `ClassLoaderAwareObjectInputStream` overrides `resolveClass()` but the buggy implementation does not resolve primitive class names after normal class-loader resolution fails.
* **Target behavior:** serialized primitive `Class` objects such as `long.class`, `boolean.class`, and `void.class` must deserialize successfully.
* **Number of generated tests:** **5**

  * **3 defect-detecting tests**
  * **2 regression tests**
* The tests directly exercise the public `SerializationUtils.serialize()` → `SerializationUtils.deserialize()` workflow.
* They do **not** invoke the supplied trigger test.
* They do **not** use `int.class`, which was identified in the supplied trigger information.
* The primitive inputs were independently selected from the fixed source's `primitiveTypes` map.
* The Apache issue independently confirms that LANG-788 is specifically about `SerializationUtils` failing to clone primitive classes because the custom resolver lacked the primitive-class fallback. ([Apache Issues][1])

### Limitations

1. The exact Defects4J trigger implementation was not used.
2. `long.class`, `boolean.class`, and `void.class` all exercise the same fundamental primitive-resolution mechanism, so they are complementary coverage rather than completely independent root causes.
3. The array and reference-class tests are regression tests; they are expected to pass on both revisions and therefore are not themselves defect detectors.
4. The tests depend on Java's standard serialization representation of `Class` objects, which is the mechanism involved in the reported defect.
5. The source supplied shows that the fixed version specifically adds mappings for the primitive names, so the expected BUGGY/ FIXED behavior is strongly supported by the source difference.
