## 1. SOURCE CODE ANALYSIS

The defect is in `StopWatch.stop()` when the stopwatch is **suspended**.

The Apache JIRA description for LANG-315 confirms the intended behavior: after `suspend()`, time should remain paused, and a subsequent `stop()` should **not add the time spent while suspended**. ([Apache Issues][1])

### Behavior difference

#### BUGGY

The BUGGY implementation allows both `RUNNING` and `SUSPENDED` states:

```java
if (this.runningState != STATE_RUNNING && this.runningState != STATE_SUSPENDED) {
    throw new IllegalStateException("Stopwatch is not running. ");
}
stopTime = System.currentTimeMillis();
this.runningState = STATE_STOPPED;
```

The problem is that `stopTime` is **always updated**, even when the stopwatch is suspended.

Therefore:

```text
start()
   ↓
suspend()
   ↓
[time is paused]
   ↓
wait
   ↓
stop()
```

causes the waiting period after `suspend()` to be included in `getTime()`.

### FIXED

The FIXED implementation changes this to:

```java
if (this.runningState == STATE_RUNNING) {
    stopTime = System.currentTimeMillis();
}
this.runningState = STATE_STOPPED;
```

So when the stopwatch is suspended:

```text
stopTime = time at suspend
```

and `stop()` does **not** replace it.

This is exactly the correction described by LANG-315. The issue was fixed in the Commons Lang 2.3 release. ([Apache Issues][1])

### Root cause

The root cause is:

> `stop()` treats `RUNNING` and `SUSPENDED` states the same when recording `stopTime`, even though a suspended stopwatch must preserve the timestamp recorded by `suspend()`.

## 2. TEST CASE DESIGN

The most direct way to expose the defect is:

1. Start the stopwatch.
2. Allow some measurable time to pass.
3. Suspend it.
4. Record `getTime()`.
5. Wait again while it is suspended.
6. Call `stop()`.
7. Check that `getTime()` has **not changed**.

The important assertion is:

```java
timeAfterSuspend == timeAfterStop
```

This is much stronger than checking an approximate duration because the FIXED implementation preserves the exact `stopTime` recorded by `suspend()`.

### Test 1 — stop after suspension

Representative defect case:

```text
start
→ wait
→ suspend
→ wait
→ stop
```

Expected:

```text
time after suspend == time after stop
```

This directly detects the defect.

### Test 2 — longer suspended interval

Use a different timing pattern:

```text
start
→ wait
→ suspend
→ wait longer
→ stop
```

This checks that the amount of time excluded while suspended does not accidentally get included.

### Test 3 — resume, suspend, then stop

This checks a more realistic lifecycle:

```text
start
→ wait
→ suspend
→ resume
→ wait
→ suspend
→ wait
→ stop
```

Only the final suspended interval must be excluded.

### Regression cases

Also include:

* stopping normally while `RUNNING` should still record the final stop time;
* stopping an unstarted stopwatch should still throw `IllegalStateException`;
* stopping an already stopped stopwatch should still throw `IllegalStateException`.

These ensure that the fix did not accidentally change unrelated state-transition behavior.

## 3. JUNIT 4.12 TEST CODE

The following class uses only the public `StopWatch` API. It does not access internal state, use reflection, or reproduce the original trigger.

The waits are intentionally short but long enough to make the buggy `stop()` behavior observable.

```java
package org.apache.commons.lang.time;

import static org.junit.Assert.assertEquals;
import static org.junit.Assert.assertTrue;
import static org.junit.Assert.fail;

import org.junit.Test;

public class StopWatchLang55Test {

    @Test
    public void testStopAfterSuspendKeepsSuspendedTime() throws Exception {
        StopWatch watch = new StopWatch();

        watch.start();
        Thread.sleep(60);
        watch.suspend();

        long timeAfterSuspend = watch.getTime();

        Thread.sleep(120);
        watch.stop();

        long timeAfterStop = watch.getTime();

        assertEquals(timeAfterSuspend, timeAfterStop);
    }

    @Test
    public void testLongerSuspensionIsExcludedWhenStopping() throws Exception {
        StopWatch watch = new StopWatch();

        watch.start();
        Thread.sleep(80);
        watch.suspend();

        long suspendedTime = watch.getTime();

        Thread.sleep(200);
        watch.stop();

        assertEquals(suspendedTime, watch.getTime());
    }

    @Test
    public void testStopAfterResumeAndSecondSuspendKeepsFinalSuspendedTime()
            throws Exception {
        StopWatch watch = new StopWatch();

        watch.start();
        Thread.sleep(60);
        watch.suspend();

        Thread.sleep(100);
        watch.resume();

        Thread.sleep(70);
        watch.suspend();

        long timeAfterFinalSuspend = watch.getTime();

        Thread.sleep(150);
        watch.stop();

        assertEquals(timeAfterFinalSuspend, watch.getTime());
    }

    @Test
    public void testNormalRunningStopStillRecordsElapsedTime()
            throws Exception {
        StopWatch watch = new StopWatch();

        watch.start();
        Thread.sleep(100);
        watch.stop();

        assertTrue(watch.getTime() >= 50);
    }

    @Test
    public void testStopBeforeStartIsRejected() {
        StopWatch watch = new StopWatch();

        try {
            watch.stop();
            fail("Expected IllegalStateException");
        } catch (IllegalStateException expected) {
            // expected
        }
    }

    @Test
    public void testStopAfterAlreadyStoppedIsRejected()
            throws Exception {
        StopWatch watch = new StopWatch();

        watch.start();
        Thread.sleep(50);
        watch.stop();

        try {
            watch.stop();
            fail("Expected IllegalStateException");
        } catch (IllegalStateException expected) {
            // expected
        }
    }
}
```

## 4. DEFECT DETECTION STRATEGY

### Test 1 — `testStopAfterSuspendKeepsSuspendedTime`

**BUGGY VERSION**

Sequence:

```text
start
→ wait
→ suspend
→ record T
→ wait
→ stop
```

During `suspend()`:

```java
stopTime = System.currentTimeMillis();
```

Then BUGGY `stop()` executes:

```java
stopTime = System.currentTimeMillis();
```

Therefore:

```text
timeAfterStop > timeAfterSuspend
```

and:

```java
assertEquals(timeAfterSuspend, timeAfterStop);
```

**fails**.

**FIXED VERSION**

After `suspend()`:

```text
stopTime = suspension timestamp
```

`stop()` sees:

```java
runningState == STATE_SUSPENDED
```

and does not update `stopTime`.

Therefore:

```text
timeAfterStop == timeAfterSuspend
```

and the test **passes**.

**Defect-detecting: YES**

---

### Test 2 — `testLongerSuspensionIsExcludedWhenStopping`

This is the same semantic condition but uses a substantially longer suspended interval.

**BUGGY:**

The additional ~200 ms is included in the final time.

```text
timeAfterStop > suspendedTime
```

Test fails.

**FIXED:**

The additional suspended time is excluded.

```text
timeAfterStop == suspendedTime
```

Test passes.

**Defect-detecting: YES**

---

### Test 3 — `testStopAfterResumeAndSecondSuspendKeepsFinalSuspendedTime`

This exercises the state transition:

```text
RUNNING
→ SUSPENDED
→ RUNNING
→ SUSPENDED
→ STOPPED
```

The important point is that the **second suspension timestamp** must remain the final stop timestamp.

**BUGGY:**

`stop()` overwrites `stopTime`, so the final suspended interval is included.

Test fails.

**FIXED:**

`stop()` preserves the second suspension timestamp.

Test passes.

**Defect-detecting: YES**

---

### Test 4 — `testNormalRunningStopStillRecordsElapsedTime`

This verifies that the fix does not break normal stopping.

**BUGGY:**

When `RUNNING`, `stopTime` is recorded.

Test passes.

**FIXED:**

When `RUNNING`, `stopTime` is also recorded.

Test passes.

**Defect-detecting: NO**

This is a regression test.

---

### Test 5 — `testStopBeforeStartIsRejected`

Both implementations reject:

```text
UNSTARTED → stop()
```

with `IllegalStateException`.

**BUGGY:** passes.

**FIXED:** passes.

**Defect-detecting: NO**

Regression/state-validation test.

---

### Test 6 — `testStopAfterAlreadyStoppedIsRejected`

Both versions reject:

```text
STOPPED → stop()
```

with `IllegalStateException`.

**BUGGY:** passes.

**FIXED:** passes.

**Defect-detecting: NO**

Regression/state-validation test.

## 5. SUMMARY

### Root cause

The BUGGY `stop()` implementation always executes:

```java
stopTime = System.currentTimeMillis();
```

even when the stopwatch is in `STATE_SUSPENDED`.

This causes time spent between `suspend()` and `stop()` to be incorrectly counted.

The FIXED implementation records `stopTime` only when the stopwatch is actually `STATE_RUNNING`. ([Apache Issues][1])

### Targeted behavior

The key invariant is:

```text
After suspend():
    getTime() = T

After waiting while suspended and calling stop():
    getTime() must still equal T
```

### Number of generated tests

**6 tests**

| Test                                                         | Purpose                  | BUGGY | FIXED |
| ------------------------------------------------------------ | ------------------------ | ----: | ----: |
| `testStopAfterSuspendKeepsSuspendedTime`                     | Direct defect            |     ❌ |     ✅ |
| `testLongerSuspensionIsExcludedWhenStopping`                 | Defect with longer pause |     ❌ |     ✅ |
| `testStopAfterResumeAndSecondSuspendKeepsFinalSuspendedTime` | State-transition defect  |     ❌ |     ✅ |
| `testNormalRunningStopStillRecordsElapsedTime`               | Regression               |     ✅ |     ✅ |
| `testStopBeforeStartIsRejected`                              | State validation         |     ✅ |     ✅ |
| `testStopAfterAlreadyStoppedIsRejected`                      | State validation         |     ✅ |     ✅ |

The first three are designed to be **defect-detecting tests**.

### Independence from the trigger

The tests are independently derived from the source-level state-machine defect. They do not invoke `testLang315`, do not use reflection, and do not require access to `startTime`, `stopTime`, or the internal state constants.

The test strategy is based on the semantic distinction:

```text
RUNNING  → stop() should update stopTime
SUSPENDED → stop() should NOT update stopTime
```

which is directly visible in the BUGGY/FIXED implementations and in the LANG-315 description. ([Apache Issues][1])

## 6. LIMITATIONS

1. **Timing-based tests inherently depend on the scheduler.** The tests use `Thread.sleep()` to make the incorrect additional elapsed time large enough to distinguish from normal timing jitter.

2. The first three tests compare `getTime()` **exactly** before and after `stop()`. This is appropriate here because the fixed implementation preserves the same `stopTime`; it does not depend on estimating elapsed milliseconds.

3. The normal-running regression test uses a lower bound rather than an exact duration because `System.currentTimeMillis()` and thread scheduling make exact timing assertions inappropriate.

4. The supplied source establishes the defect clearly, and the Apache JIRA description independently confirms that `suspend()` followed by `stop()` must not include the suspended interval. ([Apache Issues][1])

5. The tests intentionally avoid reproducing the original trigger's exact sleep durations or values. They exercise the same **behavioral condition** through independently chosen timing intervals.
