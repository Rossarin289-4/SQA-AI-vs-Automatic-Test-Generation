## 1. Behavior Difference and Root Cause

### 1.1 Behavior that differs

The defect is in the **capacity calculation** inside `StringUtils.join(...)`, not in the actual joining logic.

For an object whose `toString()` method returns `null`, the buggy implementation calculates the `StringBuilder` capacity by doing:

```java
array[startIndex].toString().length()
```

Therefore, a non-null object whose `toString()` returns `null` causes a **NullPointerException before the elements are joined**.

The fixed implementation removes this eager `toString().length()` calculation and instead uses a fixed capacity based only on the number of elements. The subsequent `StringBuilder.append(Object)` operation can safely handle an object's `toString()` returning `null`, producing the text `"null"`. The official LANG-703 commit explicitly describes the change as fixing an NPE when `toString` returns null. ([GitHub][1])

The Apache release notes also identify LANG-703 as:

> `StringUtils.join` throws NPE when `toString` returns null for one of objects in collection. ([GitHub][2])

### 1.2 Likely root cause

The buggy code performs unnecessary eager string conversion solely to estimate the buffer size:

```java
bufSize *= ((array[startIndex] == null ? 16 :
    array[startIndex].toString().length()) + 1);
```

and similarly for the `String` separator overload:

```java
bufSize *= ((array[startIndex] == null ? 16 :
    array[startIndex].toString().length())
    + separator.length());
```

This assumes that `toString()` on a non-null object must return a non-null `String`. That assumption is invalid because Java permits an overridden `toString()` method to return `null`.

The fixed revision replaces this calculation with:

```java
StringBuilder buf = new StringBuilder(noOfItems * 16);
```

so the buffer-size optimization no longer calls `toString()` prematurely. ([GitHub][1])

## 2. Specific Behavior and Independent Test Design

The key oracle should be:

> A non-null object whose `toString()` returns `null` must be treated as producing `"null"` when joined.

This is consistent with the actual fixed revision's regression expectation: the official patch added an object with `toString()` returning `null` and expected `"null"`. ([GitHub][1])

I would use **four complementary tests**.

| Test | Scenario                                                     | Buggy                  | Fixed    |        |
| ---- | ------------------------------------------------------------ | ---------------------- | -------- | ------ |
| 1    | One custom object, no separator                              | `NullPointerException` | `"null"` |        |
| 2    | One custom object with char separator and restricted range   | `NullPointerException` | `"null"` |        |
| 3    | One custom object with String separator and restricted range | `NullPointerException` | `"null"` |        |
| 4    | Null-returning object followed by normal object              | `NullPointerException` | `"null   | tail"` |

These are deliberately not copies of the trigger implementation. In particular, they use different object text and separator choices and exercise different overload paths.

### Boundary cases considered

* `null` array itself — existing contract behavior; not the defect.
* empty array — existing contract behavior.
* actual `null` element — different from an object whose `toString()` returns `null`.
* one-element array — important because it directly exercises the capacity calculation.
* null-returning object as the first element — important because the buggy capacity calculation examines `array[startIndex]`.
* multiple elements — confirms the defect is not limited to the one-element result path.
* restricted `startIndex/endIndex` overloads — exercises the actual modified overload directly.

The crucial distinction is:

```java
null
```

versus

```java
new Object() {
    public String toString() {
        return null;
    }
}
```

The latter is non-null but has a null textual representation.

## 3. Complete JUnit 4.12 Test Class

```java
package org.apache.commons.lang3;

import static org.junit.Assert.assertEquals;

import org.junit.Test;

public class StringUtilsLang20Test {

    private static final Object NULL_TO_STRING_OBJECT = new Object() {
        @Override
        public String toString() {
            return null;
        }
    };

    @Test
    public void testJoinSingleObjectWhoseToStringReturnsNull() {
        Object[] values = { NULL_TO_STRING_OBJECT };

        assertEquals("null", StringUtils.join(values));
    }

    @Test
    public void testJoinCharRangeWithNullReturningToString() {
        Object[] values = {
            "prefix",
            NULL_TO_STRING_OBJECT,
            "suffix"
        };

        assertEquals(
            "null",
            StringUtils.join(values, ':', 1, 2)
        );
    }

    @Test
    public void testJoinStringRangeWithNullReturningToString() {
        Object[] values = {
            "left",
            NULL_TO_STRING_OBJECT,
            "right"
        };

        assertEquals(
            "null",
            StringUtils.join(values, "::", 1, 2)
        );
    }

    @Test
    public void testJoinMultipleObjectsWhenFirstObjectToStringReturnsNull() {
        Object[] values = {
            NULL_TO_STRING_OBJECT,
            "tail"
        };

        assertEquals(
            "null|tail",
            StringUtils.join(values, "|")
        );
    }
}
```

## 4. Defect Detection Strategy

### Test 1 — `testJoinSingleObjectWhoseToStringReturnsNull`

**Input**

```text
[object whose toString() returns null]
```

using the no-separator `join(Object[])` API.

**BUGGY VERSION**

The call eventually reaches the `String`-separator implementation. Before constructing the buffer, the buggy implementation executes:

```java
array[startIndex].toString().length()
```

Since `toString()` returns `null`, this becomes:

```java
null.length()
```

Therefore:

**Expected:** `NullPointerException`

The test expects `"null"`, so **the test fails on BUGGY**.

**FIXED VERSION**

The fixed implementation no longer calls `toString()` during capacity calculation. The object is subsequently appended normally, resulting in:

```text
"null"
```

Therefore:

**Expected:** `"null"`

**Result:** test passes.

---

### Test 2 — `testJoinCharRangeWithNullReturningToString`

This test uses:

```java
StringUtils.join(values, ':', 1, 2)
```

so the selected range contains exactly one object whose `toString()` returns `null`.

**BUGGY VERSION**

The char-array/object-array range implementation performs the same problematic capacity calculation on the selected first element.

**Expected:** `NullPointerException`

Therefore the assertion fails.

**FIXED VERSION**

The capacity calculation no longer calls the object's `toString()`.

The selected single element is joined as:

```text
"null"
```

**Expected:** `"null"`

Therefore the test passes.

---

### Test 3 — `testJoinStringRangeWithNullReturningToString`

This test specifically exercises the overload:

```java
join(Object[], String, int, int)
```

with a multi-character separator.

The selected range still contains only the object whose `toString()` returns `null`.

**BUGGY VERSION**

The capacity calculation evaluates:

```java
array[startIndex].toString().length()
```

and therefore throws `NullPointerException`.

**FIXED VERSION**

No eager `toString()` call is performed.

The single selected object is represented as:

```text
"null"
```

so the test passes.

---

### Test 4 — `testJoinMultipleObjectsWhenFirstObjectToStringReturnsNull`

This test checks that the problem also occurs when there are **multiple objects**, rather than only when the result consists of one object.

Input conceptually is:

```text
[
    object.toString() -> null,
    "tail"
]
```

with `"|"` as the separator.

**BUGGY VERSION**

The buggy implementation estimates the buffer size from the first object before entering the joining loop:

```java
array[startIndex].toString().length()
```

The first object's `toString()` returns `null`, so a `NullPointerException` occurs.

**Expected:** `NullPointerException`

Thus the test fails.

**FIXED VERSION**

The fixed implementation skips that unsafe capacity calculation and performs the actual append operations.

The result is:

```text
null|tail
```

Therefore:

**Expected:** `"null|tail"`

The test passes.

## 5. Summary

* **Root cause:** `StringUtils.join` performed an eager `toString().length()` call to estimate `StringBuilder` capacity.
* **Defect:** A non-null object whose `toString()` returns `null` caused `NullPointerException` during this capacity calculation.
* **Correct behavior:** The object should still be joinable; its textual representation is handled as `"null"` by the normal append operation.
* **Targeted behavior:** `StringUtils.join` with objects whose `toString()` returns `null`.
* **Generated tests:** **4**
* **Detection expectation:** all four tests should **fail on the buggy version and pass on the fixed version**.
* **Independence:** The tests are derived from the source-level failure mechanism rather than reproducing the Defects4J trigger test. They use a newly designed null-returning object, different surrounding values, different separators, and separate overload/range scenarios.

The actual LANG-703 patch confirms that the production change was specifically to remove the unsafe `toString().length()` capacity calculation, while its added regression object overrides `toString()` to return `null`. ([GitHub][1])
